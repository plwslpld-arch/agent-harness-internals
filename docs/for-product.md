# 产品视角：用户看到的现象，背后是哪条机制

*这一篇讲给产品经理和交互设计。用「用户能观察到的现象」当索引，每条给出背后的机制、各家的不同选择、以及要深挖时去看哪一篇。不需要读代码。*

用户提的 bug 常常不是 bug。「AI 越聊越笨」是压缩把原文换成了摘要；「切个模式怎么卡这么久」是那一下把请求开头改了、几万 token 全要重算；「我改了 AGENTS.md 它没看见」是那份文件压根不是每次都读的。这些都不是模型的锅，是 harness 某个具体决定的直接后果，而那个决定往往是产品侧当初随手定的。

下面按「用户能观察到的现象」编排，每条给出背后是哪条机制、各家怎么选、以及这个选择在产品上花了什么代价。

如果你还不清楚 harness 是什么，先看 [不写代码也要懂的：agent harness 到底是什么](concepts.md)。

---

## 一、成本与性能

### 现象 1：同一个任务，聊到后面明显变慢、变贵

**机制**：模型没有记忆，每轮都把全部历史重发一遍。第 50 轮发的量可能是第 1 轮的几十倍。

**决定体验的关键**：请求开头那段有没有保持不变。服务端的前缀缓存逐字比对，开头改一个字，后面全部作废。

**实测**（我们自己用真实 API 跑的，记录在 `research/runtime-evidence/`）：开头不动、只在末尾追加时命中 81%–96%；把开头第一句改几个字，命中率 **0%**。

**各家做法**：DeepSeek 和 OpenAI 是服务端自动匹配前缀，客户端基本只能「别去动它」（OpenAI 侧还留了一个把会话 ID 当缓存键的旋钮）；Anthropic 是另一套模型，要客户端显式打最多 4 个缓存断点，Claude Code 把断点分成四层（静态部分 → 项目说明 → 会话上下文 → 对话消息）。

**深读**：[02 KV-Cache](02-kv-cache.md)

---

### 现象 2：切换权限模式后，那一次回复特别慢

**机制**：如果这条状态被写进请求开头，切换就等于改开头，整段缓存作废，几万 token 要重算。

**实测**：写在开头时，切换后只剩 256 个 token 命中（33%）；改成追加在末尾时保持 81%。dsh 选了后者，上游为此专门留了一条设计记录。

**产品启发**：任何「用户可以随时切换的状态」（模式、权限、模型选择、语言）都要问一句：它进请求的哪个位置。用户感觉不到差别，账单和延迟能感觉到。

**深读**：[01 System Prompt](01-system-prompt.md) 的运行时快照一节

---

### 现象 3：切换模型之后，前面聊的全部要重算

**机制**：缓存是绑在具体模型上的。换模型 = 换一个缓存域，之前攒的全部作废。

同一类操作在 Claude Code 上也会失效。本仓库核到的两条是 MCP 服务连断、按工具名整体禁用某个工具，两条都改动了工具定义；其余像切模型、执行 `/compact`，机制上同理，官方缓存文档里有，本仓库没有逐条核验。

**产品启发**：「一键切换模型」这个功能在长对话里是有代价的，值得在 UI 上给用户一个提示，或者干脆限制在新会话才能切。

**深读**：[02 KV-Cache](02-kv-cache.md) 的「其它场景逐一」

## 二、上下文与遗忘

### 现象 4：聊久了它开始忘事，刚说过的细节要重复告诉它

**机制**：上下文快满时触发压缩，把前面一大段对话交给模型总结成摘要，用摘要替换原文。原文里的细节就此丢失。

**各家保留策略**：

| 产品 | 压完还保留什么 |
|---|---|
| Claude Code | 明确的「幸存清单」：项目说明文件和记忆从磁盘重新读入，已加载的 skill 正文重新注入（单个上限 5k token、总计 25k） |
| Codex | 本地实现保留 ≤20k token 的用户消息 + 摘要，assistant 和工具结果全丢 |
| dsh | 从最早开始压，保留末尾一段，绝不拆散「工具调用」和「它的结果」 |
| pi | 保留最近 20k token，绝不在工具结果处切断 |
| mini-swe-agent | 不压缩，撞上限直接结束任务 |

**产品启发**：压缩是必然会发生的，问题是**用户知不知道它发生了**。目前多数产品是静默的，用户只感觉到「AI 变笨了」。给一个明确提示（「已压缩上下文，早期细节可能丢失」）成本很低，对信任的帮助很大。

**深读**：[06 压缩](06-compaction.md)

---

### 现象 5：压缩那一下要等很久

**机制**：压缩本身要发一次大请求，把前面全部内容发给模型让它总结。

**dsh 的做法**：让这次总结请求跟主对话的开头**逐字节相同**，于是这部分也能命中缓存。实测命中 93.4%；作为对照，给总结任务另写一段开头的写法是 **0%**。

pi 走的是相反的路：给总结请求换一个会话 ID 并禁止写缓存，避免污染主会话的缓存分片。两种思路针对不同的计费模型，都成立。

**产品启发**：Claude Code 有个更省的替代动作 `/rewind`，回退到一个已经缓存过的位置，比压缩便宜。值得考虑给用户这个选项。

**深读**：[06 压缩](06-compaction.md)

---

### 现象 6：项目里的 AGENTS.md / CLAUDE.md 改了，但 AI 好像没看到

**机制**：这类项目说明文件不是每次都重读的。

- **dsh**：只有当模型用 read / write / edit 工具动过文件时才重新检查。**你在终端里用编辑器改的，它看不见。**
- **Claude Code**：目录树向上全量拼接，子目录惰性加载。压缩之后会把项目根的 CLAUDE.md 从磁盘重新读一遍，所以一次 `/compact` 反而能让改动生效。
- **OpenCode**：向上找到第一个匹配的文件就停，不会把所有祖先目录的都堆上；子目录同样是惰性的，模型真读到那个目录的文件时才补进来。

**产品启发**：这是个高频困惑点。要么做文件监听，要么在 UI 上明说「改完请重开会话」。

**深读**：[01 System Prompt](01-system-prompt.md) 的注入链一节

## 三、权限与安全

### 现象 7：有时候弹窗问我，有时候直接就干了

**机制**：这里是两套独立机制。**审批**决定「要不要跑」，**沙箱**决定「跑起来能碰到什么」。

**容易误解的一点**：dsh 默认组合下，写文件和跑命令**不弹窗**。默认组合里弹窗的唯一入口是模型自己在被沙箱拒绝后申请提权。（机制上还有第二条路，某个 hook 返回「要问」，但默认组合没挂任何 hook 桥。）

| 产品 | 审批 | 系统级沙箱 |
|---|---|---|
| Claude Code | 6 种权限模式，其中一种用第二个模型当自动审核员（这一行依据官方公开文档，无法从源码核实） | macOS/Linux 有，**原生 Windows 没有** |
| Codex | 四档策略 + 「被拒后申请提权」的三段式流程 | 三平台都有 |
| dsh | 默认不弹窗，靠沙箱兜底 | 有 |
| OpenCode | 完整规则引擎，能解析 bash 命令结构 | **没有** |
| pi | **刻意不做**，建议跑在容器里 | 没有 |

**产品启发**：「有没有权限管理」问不到点子上。要问「是审批还是沙箱、原生 Windows 上有没有」。另外，让用户点习惯「同意」的设计等于没有防护。

**深读**：[07 工具、审批与沙箱](07-tools-approval-sandbox.md)

---

### 现象 8：它说「我改不了这个文件」，但明明有权限

**机制**：沙箱在操作系统层面拦住了，模型只拿到一句「被策略拒绝」。dsh 的工具描述里专门写了这句：这是策略拒绝，不是命令本身有 bug，**不要换个方式重试**。

**产品启发**：这类错误提示要区分「你没权限」和「命令写错了」，否则模型会陷入无意义的重试循环，用户也搞不清状况。

**深读**：[07 工具、审批与沙箱](07-tools-approval-sandbox.md)

## 四、行为与可控性

### 现象 9：同样一句话，在不同工具里表现差别很大

**机制**：模型看到的 system prompt 完全不同。

dsh 的默认 system prompt **极简**：一句身份、一句角色设定、每个工具一句使用习惯，再加 Web 特有的三段环境说明。默认 Web 组合下数出来是 18 段（换 preset 或换成 headless，段数会变）。**没有**「回答要简洁」「注意代码风格」「不要过度承诺」这类行为规范。

对比之下，OpenCode 按模型家族分发不同的主提示词（Claude 系一份、GPT 系一份、Gemini 一份），承认「同一段提示词在不同模型上效果不同」。

**产品启发**：如果你的产品基于 dsh，**行为质量高度依赖你自己写的 persona 和项目说明文件**，开箱默认体验会偏薄。这是个刻意的设计选择（harness 不替部署方做产品决策），但要知道这笔账在哪。

**深读**：[01 System Prompt](01-system-prompt.md)

---

### 现象 10：模型明明该用工具，却自己编了个答案

**机制**：工具的说明文字（description）是模型判断「什么时候该用这个工具」的唯一依据。dsh 有一条明确的分工原则：**单次调用的语义写在工具描述里，跨调用的习惯写在 system prompt 里，部署角色写在 persona 里**。每个事实只有一个归属地。

**产品启发**：工具描述是产品文案的一部分，值得像写用户文案一样打磨。dsh 里 `bash` 这一个工具的描述就有 1,836 个字符。

**深读**：[01 System Prompt](01-system-prompt.md)、[07 工具、审批与沙箱](07-tools-approval-sandbox.md)

---

### 现象 11：进入「计划模式」之后感觉变慢了

**机制**：dsh 的 plan 模式会往 system prompt 中段插一段提示，那一段往后的内容全部要重新预填。工具表倒是一字没动（进出计划模式的工具始终注册着），所以作废的只是后半截，不是整个前缀。上游在代码注释里明确接受了这个代价。

Claude Code 的做法更彻底：把模式切换本身做成两个**工具**（进入计划模式 / 退出计划模式），提示词和工具集都不动，缓存完全不受影响。

**产品启发**：「模式切换」这个交互有一个便宜的实现方式和一个贵的实现方式，值得在设计阶段就问清楚。

**深读**：[02 KV-Cache](02-kv-cache.md)、[08 编排层](08-orchestration.md)

---

### 现象 12：后台任务跑完了，但 AI 没反应

**机制**：dsh 的工具说明里写了规矩：**不要空转轮询等它**，任务完成时运行时会主动通知；给最终答复之前要把还相关的后台任务收回来。

**产品启发**：「后台任务 + 完成通知」这套交互，模型侧的规矩要写进工具描述，UI 侧还要给用户一个可见的任务列表。两边缺一个，用户就会看到「它好像忘了这件事」。

**深读**：[08 编排层](08-orchestration.md)

## 五、可靠性

### 现象 13：崩溃或断网之后，能不能接着跑

**机制**：会话怎么存的决定了这件事。

| 产品 | 存储 | 能力 |
|---|---|---|
| dsh | 只追加的事件日志（JSONL 或 SQLite 可换） | 模型看到的历史是日志的投影；崩溃后可修复 |
| Claude Code | 每会话一个 JSONL | 支持继续、恢复、分叉会话、检查点回退 |
| Codex | JSONL + SQLite 索引 | 恢复时能复原「世界状态」基线；支持分叉和回滚 |
| OpenCode | 消息落 DB，按 part 流式写入 | 中断后重开即可继续；能撤销到某条消息，但**不能分叉** |
| pi | JSONL **树**结构 | 分支是存储结构自带的能力 |
| mini-swe-agent | 每步覆写完整轨迹 | 可复现，**不能恢复** |

**产品启发**：「能不能恢复」和「能不能分叉」是两个不同的能力。分叉（从某一步开出一条新路）在调试和探索场景里很有用，但需要存储结构支持。

**深读**：[05 Session](05-session.md)

---

### 现象 14：同一个提问，两次结果差别很大

**机制**：除了模型本身的随机性，还有一层常被忽略：**提示词、工具集、工具顺序都是变量**。

dsh 把工具顺序做成了确定的（默认按名字排序，跨机器一致），因为注册顺序会随插件加载时序抖动，抖动会同时影响缓存和模型行为。

**产品启发**：做 A/B 测试或质量评测时，只对齐「模型名」是不够的。要记下完整配置：提示词版本、工具集、工具顺序、压缩是否触发过。

**深读**：[01 System Prompt](01-system-prompt.md)、[14 横向对照](14-comparison.md)

## 六、选型时该问的问题

把上面串起来，评估任何一个 AI 编程工具时，这几个问题比「支持哪些模型」更有区分度：

1. **会变的状态放在请求的什么位置？**（决定长会话成本，差距可以是几倍）
2. **压缩什么时候触发、砍哪一段、压完还保留什么？**（决定「忘事」的体验）
3. **是审批还是沙箱？原生 Windows 上有没有沙箱？**（决定安全边界是真的还是纸面的）
4. **项目说明文件什么时候重新读取？**（高频困惑点）
5. **会话能不能恢复？能不能分叉？**
6. **默认 system prompt 里有多少行为规范？**（决定开箱体验和你要自己补多少）
7. **模式切换是改提示词还是切工具？**（决定切换的代价）

完整的机制对照见 [14 横向对照](14-comparison.md)。

## 自检

**Q1：产品同学提「我们加个开关，让用户随时切换回答风格」，你要追问什么？**

追问这个开关的状态写到请求的哪个位置。如果拼进 system prompt，每切一次整段缓存作废，长会话里这一下可能要重算几万 token；如果作为一条新消息追加在末尾，前面全部照常命中。实测两者差距是 33% 对 81%。另一个更省的思路是把切换做成工具（Claude Code 的模式切换就这么做），工具集不变，缓存完全不受影响。

**Q2：用户反馈「AI 越聊越笨，前面说过的都忘了」，怎么定位？**

先确认是不是触发了压缩。压缩会把早期对话换成摘要，细节必然丢失，这是机制决定的，不是模型退化。接下来问三件事：触发阈值是多少、砍的是哪一段、压完哪些内容会被重新注入。Claude Code 有明确的幸存清单（项目说明和记忆从磁盘重读），dsh 是从最早的消息开始砍并保留末尾。产品上能做的改进通常不是「别压缩」，而是让用户**知道**压缩发生了。

**Q3：为什么说「默认不弹窗」不等于「不安全」？**

因为审批和沙箱是两层。dsh 默认不弹窗，但文件操作被限制在工作区内，模型再来申请提权时才弹窗。反过来，一个只有审批没有沙箱的产品（比如 OpenCode），在用户点习惯「同意」之后就没有第二道防线了。

也别把「有沙箱」当成万能：dsh 的 `bash` 走的是操作系统级隔离，`write` / `edit` 走的是进程内的路径围栏；而且沙箱只管文件，不管网络，模型在 `bash` 里 `curl` 一个内网地址是拦不住的。真正该问的是「哪一种、管到哪一层、原生 Windows 上有没有」。Claude Code 在最后一项上是没有的。
