# Aider：Repository Map 与 Architect Editor 分工

## 为什么值得单独看

Aider 有两个很适合拆开观察的机制，其中 Repository Map 会在有限的令牌预算内投影仓库结构，让模型接触聊天文件之外的相关符号，而 Architect 模式则把形成方案和编辑文件分成两个阶段，还允许它们使用不同模型与编辑格式。前者回答「上下文里放什么」，后者回答「建议怎样交给编辑器实施」。

这两个机制都能让大型代码库更容易操作，但它们没有消除证据缺口，因为压缩后的 Map 仍可能省略关键文件，Architect 也可能在上下文不完整时提出方案，Editor 随后还可能把正确建议应用错。本文只讲锁定源码里可以核对的选择与交接逻辑，不会因为模型表现不错、生成了提交或测试碰巧一次通过，就把它们当成任务正确的证明。

## 机制一：Repository Map；机制二：Architect 与 Editor

`RepoMap.get_repo_map` 会先检查令牌预算和其他文件集合，如果预算为零，或者根本没有其他文件，它就不会生成映射。通过检查后，它接收聊天文件、其他文件、被提及的文件与标识符，再调用排序标签映射，而在没有聊天文件时，它还可以在上下文窗口扣除预留空间后扩大仓库视图。

Repository Map 是一份经过排序的上下文投影，它靠符号和引用提高每个令牌承载的信息量，却既不包含完整文件内容，也不保证选中每一项依赖。由于 `map_tokens`、上下文窗口、提及线索和排序结果会共同决定模型最终看见什么，所以复现实验不能只留下预算配置，还要保存最终 Map 的内容或哈希。

ArchitectCoder 继承 AskCoder，并先形成架构或修改建议。当回复已经完成、内容非空而且没有开启自动接受时，它会询问用户是否继续编辑文件，获准后再选择主模型配置中的 editor_model。如果没有独立 Editor，它就退回主模型，同时设置 editor_edit_format，随后创建新的 Coder，把 Architect 的内容作为消息交给 Editor 执行。

这次交接把自然语言方案和结构化编辑协议分开，因此 Architect 可以专注分析，Editor 可以专注应用 diff 或整文件格式，不过两者也可能指向同一个模型对象。是否真的经过人工确认取决于 `auto_accept_architect`，所以只有当有效配置关闭自动接受，并且确认交互确实发生时，才能说「Architect 模式有人审」。

Editor 完成后，Architect 会接收总成本与 Aider 产生的提交哈希，并把当前消息移回上文。这里的提交哈希属于产物血缘——只能说明某次编辑形成了 Git 对象，既不能说明需求已经满足，也不能排除测试被错误修改的可能。Git 记录和任务评分必须分开。

## 从哪里开始读源码

可以从 [`RepoMap.get_repo_map`](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py#L103-L135) 开始，先核对提前返回条件、预算放大和 `get_ranked_tags_map` 调用，如果还需要解释排序，再进入标签图、缓存与排名实现，并记录哪些文件被当作 chat_files 与 other_files。只看最终 Map 文本，很难追到遗漏发生在哪一步。

接着读 [`ArchitectCoder.reply_completed`](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/architect_coder.py#L6-L48)，因为空回复处理、人工确认、Editor 模型选择、编辑格式、Coder 创建、建议交接和提交哈希回收都集中在这里。继续分析时还要连到模型配置，确定 editor_model 究竟是独立模型，还是主模型的别名。

## 把两段源码连成因果链

Repository Map 与模型上下文真正接上的地方，不是 `map_tokens` 这项配置本身，而是最终 Map 文本进入了哪一次请求。教学实现应保存候选文件集合、符号排序、预算裁剪和最终内容哈希，并把这个哈希关联到 Architect 请求，这样方案一旦漏掉依赖，复核者就能判断是源文件没有被扫描、排名太低、预算裁剪，还是模型忽略了已经提供的信息。

Architect 与 Editor 之间靠一份带来源的建议消息衔接，交接对象至少要记录 Architect 模型、输入 Map、原始建议、确认决定、Editor 模型、编辑格式和新 Coder 标识。如果用户拒绝，就不能创建 Editor。即使两个阶段使用同一模型，也要留下两个调用边界，不能因为模型 ID 相同，就把规划与编辑压成一次无法解释的请求。

编辑器与产物通过文件差异、命令结果和提交哈希衔接，虽然提交能提供不可变引用，但未追踪文件、工作树残留和外部副作用仍要单独收集。最小实验可以故意让 Architect 给出正确建议，却让 Editor 改错一行，再让另一轮 Map 漏掉关键符号。前一种失败属于交接，后一种属于上下文投影——不能都笼统归为模型失败。

## 沿一次任务走完整链

1. 入口确定聊天文件、其他仓库文件、提及文件与标识符，并计算 Map 预算。
2. RepoMap 对符号与引用排序，生成受上下文窗口约束的仓库投影。
3. Architect 读取任务、聊天文件和 Map，输出可执行的修改建议。
4. 根据有效配置等待用户确认或自动接受，再选择 Editor 模型与编辑格式。
5. Editor Coder 接收建议，修改文件并可能运行命令、测试或创建 Git 提交。
6. 外部验收比较最终差异、测试与需求，独立决定任务是否通过。

可观测记录至少要包含 Map 预算、最终 Map、Architect 原始建议、确认决定、Editor 模型与格式、文件差异、命令和提交哈希。如果只保留最终提交，就无法判断错误来自上下文选择、规划还是编辑，而只保留聊天又无法证明磁盘上究竟产生了什么。

## 它补充了六条主课程的什么

Aider 这个扩展样本补充了代码上下文压缩与规划编辑分工，而六条一级主线会覆盖更完整的运行时、会话、权限和产品表面。这里不做综合排名，也不把 Repository Map 当作所有 Harness 都该复制的唯一方案，它真正提供的是一套可以迁移的问题框架，上下文投影怎样产生、缺口怎样发现，以及角色交接怎样保留血缘。

在独立核对时，Map 和 Architect 建议属于运行 Trace，文件差异和 Git 对象则属于环境产物，因此 Evaluator 应读取冻结任务与最终产物，而不能把 Architect 提出建议、Editor 正常结束或 Git 生成提交直接算作通过。

## 什么时候值得采用

Repository Map 适合符号关系丰富、完整仓库又放不进上下文的代码任务。面对只有少量文件、以非代码资源为主、语言不受解析器支持，或者依赖主要来自运行时配置的项目时，Map 可能增加成本，却仍然漏掉核心事实。扩大预算也不会无限带来收益，因为更多符号会挤占任务、历史和工具结果的空间，实际效果必须按任务验证。

Architect/Editor 分工适合方案需要复核、编辑格式需要专门处理，或模型角色可以分别分配的场景，不过极小修改反而可能因为额外调用而增加延迟和误差，自动接受也会去掉人工检查边界。本文只覆盖锁定源码中的 Map 与交接机制，不评价 Aider 的全部模式、真实模型质量或任何部署的默认安全。迁移时要复制问题与记录方式，不必照搬类名。

## 最容易误判的地方

Map 的主要风险来自信息选择偏差，因为关键实现可能由于预算不足、解析失败或图排名较低而缺席，模型却容易把眼前的投影当成完整仓库。另一个风险来自角色标签造成的能力幻觉，Architect 与 Editor 这两个名称既不能证明它们使用不同模型，也不能证明方案经过人工复核。

还要防止把 Git 当作完成门槛，因为自动提交虽然提高了可追溯性，却可能包含错误更改、漏掉未追踪文件，甚至通过修改测试来迎合结果。命令返回零和提交生成都只是运行信号，必须结合冻结任务、禁止项和独立测试来解释。

## 怎样亲手核对

可以准备一个跨越三个文件的受控任务，并把关键符号放在聊天文件之外，然后分别用充足和极小的 Map 预算运行，记录最终 Map 是否包含该符号，以及缺失与否怎样影响方案。这个实验只验证上下文投影链，单个模型的结果不能代表普遍性能。

进行 Architect 实验时先关闭自动接受，确认用户拒绝后不会创建 Editor，再批准一次并固定独立 editor_model 与格式，检查 Editor 收到的内容是否等于 Architect 建议。这一步不能省。最后用外部测试验证文件产物，并故意构造一个「提交成功但需求做错」的案例，确认门禁不会把提交本身当成通过。

## 读完后做四个判断

### 问题 1

Repository Map 是完整源码吗？

**答案：** 不是，它是受预算和排序约束的符号投影。

### 问题 2

Architect 与 Editor 一定使用不同模型吗？

**答案：** 不一定，没有独立 Editor 时会回退主模型。

### 问题 3

Architect 模式一定有人确认吗？

**答案：** 不一定，自动接受配置会改变这条边界。

### 问题 4

生成 Git 提交能否计为完成？

**答案：** 不能，仍需按任务契约验证差异、测试和副作用。
