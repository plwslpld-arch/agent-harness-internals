# goose：Recipe 与 Extension 的分阶段装配

## 样本定位

goose 的独特样本价值在于把可复用工作流输入与外部能力装配放到同一条可核对链上。Recipe 描述标题、指令、启动提示、参数、扩展和设置；Agent 与 ExtensionManager 再把扩展连接到具体会话并汇总工具。这种结构便于复用任务，但也容易产生「配置里写了扩展，所以模型一定能调用」的错误推断。

本文把扩展能力拆成五个阶段：配置被发现、配置被解析、扩展连接成功、工具对模型可见、工具获准并真实执行。只有完整记录这些阶段，才知道失败发生在配方、依赖、协议、模型选择还是权限层。Recipe 不是评测结果，工具清单也不是任务完成证据。

## 独特机制

`Recipe` 数据结构要求版本、标题和描述，并允许提供模型 instructions、启动 prompt、extensions、settings 与活动提示。源码注释要求 instructions 或 prompt 至少出现一个，使配方既可以设置持续指令，也可以直接启动一次会话。Claim: goose.recipe-binds-instructions-and-extensions。

Recipe 把扩展配置与模型输入放在同一可移植对象里，却没有把扩展运行结果写死。参数替换、嵌套配方、工作目录与用户配置可能共同影响最终值，所以实验血缘应保存解析后的有效 Recipe，而不只是原始 YAML。活动提示属于交互展示，也不能作为执行阶段的证据。

会话构建器把待加载扩展整理成名称与配置对，然后调用加载函数。Agent 的 `add_extension` 先执行内部装载，成功后才持久化扩展状态；普通扩展按会话工作目录交给 ExtensionManager，前端扩展走独立插入分支。之后 `list_tools` 从 ExtensionManager 取前缀化工具，并合并前端工具。Claim: goose.extension-tools-require-successful-load。

这个顺序非常重要。配置被发现只说明候选存在；装载成功说明客户端或前端注册完成；列出工具说明当前会话拥有候选表面；模型是否看到还取决于上下文构造和过滤；真实调用又取决于模型选择、权限与执行结果。持久化扩展状态只记录成功装载后的状态，不保证下次进程启动时外部命令、网络和凭证仍然可用。

## 源码入口

先读 `source:goose:crates/goose/src/recipe/mod.rs:42` 到 `70`，建立 Recipe 字段与责任表。继续读 builder 与验证代码时，重点核对参数需求、模板渲染和子配方怎样形成最终指令。不要从示例 Recipe 推断默认配置，因为示例只证明一种可写形式。

扩展链从 `source:goose:crates/goose/src/agents/agent.rs:1453` 到 `1587` 最容易观察：成功装载、按会话持久化、前端与普通扩展分支、工作目录传递和工具汇总都在同一段。若研究协议细节，再进入 `extension_manager.rs` 与 MCP client，核对连接、工具命名和调用路由。

## 运行链

1. CLI、桌面或调度入口取得 Recipe，并解析参数、指令、启动提示与扩展列表。
2. 会话建立 Provider、工作目录和有效提示，整理需要加载的 ExtensionConfig。
3. 普通扩展由 ExtensionManager 建立客户端，前端扩展由宿主登记；失败保持显式错误。
4. 成功装载后记录会话扩展状态，再汇总前缀化工具与前端工具。
5. 工具表进入模型可见能力，模型产生调用后再经过权限、检查与真实执行。
6. 轨迹、产物与冻结 Recipe 进入独立评分，决定 Trial 结果。

建议给每个扩展分配稳定名称，并记录配置哈希、连接方式、服务版本、发现工具列表、过滤后工具列表、调用 ID、权限决定和返回结果。对动态 MCP 服务，还要记录连接时刻和能力变化，避免用启动后的新工具解释启动前的运行。

## 与一级主线的关系

goose 不成为第七条一级主线。它补充的是 Recipe 驱动编排和会话级扩展装配，这两个机制可以反向检验六条一级主线：配置是否只被发现，扩展是否真正连接，工具是否进入模型请求，权限是否在调用时生效，失败是否保留到轨迹。

对于 Eval，Recipe 是很好的可复现实验输入，但仍需固定来源 Commit、Provider、模型、扩展服务和工作目录。Evaluator 读取真实产物，RewardAdapter 明确训练转换，候选选择与发布留出集分责。用同一 Recipe 成功启动多个会话不代表结果具有统计独立性，也不能把 Attempt 数量当成 Trial 数量。

## 失败与限制

第一类风险是目录即能力：发现 Recipe 或 Extension 配置不证明装载。第二类是连接即调用：MCP 握手和工具列表成功不证明模型收到、选择或获准使用某工具。第三类是持久化即稳定：扩展状态写入会话后，外部二进制、端口、凭证或网络仍可能在恢复时失效。

Recipe 还可能携带不受信任的指令和文件参数。解析成功并不等于内容安全，扩展返回的文本也可能影响模型后续决策。需要把输入来源、信任级别、工作目录和权限策略一同冻结，并对高风险工具增加外部隔离。

## 验证方法

建立一个只提供只读工具的测试扩展和一个故意连接失败的扩展。用同一 Recipe 分别运行，验证失败扩展不进入工具表，成功扩展被前缀化并绑定当前会话。然后禁止该工具，确认可见与可执行被正确区分。保存解析后的 Recipe 和每阶段事件。

再做恢复实验：成功装载后关闭外部服务并恢复会话，检查持久化状态不会被误判为当前可达。任务评测单独检查期望文件或结构化输出，不因 Recipe 加载或工具调用返回成功而提前判定通过。

## 自检

### 问题 1

Recipe 中声明 Extension 是否等于启用？

**答案：** 不等于，还要解析、连接并进入当前会话工具表。

### 问题 2

工具出现在列表中是否一定被模型调用？

**答案：** 不一定，还受上下文、模型选择、权限和执行错误影响。

### 问题 3

扩展状态持久化是否保证恢复成功？

**答案：** 不保证，外部依赖可能已经变化或不可达。

### 问题 4

Recipe 能否直接作为发布评测？

**答案：** 它是可复现输入的一部分，仍需独立任务、评分器和发布门槛。
