# Cline：工具批准与可恢复工作区

## 样本定位

Cline 的扩展样本聚焦两个经常被混在一起的控制问题：工具是否可以执行，以及文件改动是否可以恢复。前者由运行时工具策略、客户端批准回调和执行器共同决定；后者由可选的 Git Checkpoint 机制承担。把两条链分开后，才能避免用「用户点了批准」推断系统安全，也避免用「可以回滚」推断所有副作用都可逆。

当前锁定源码同时包含 SDK 化的 Agent Runtime、Core、Shared 类型与多种宿主表面。本文只总结能从锁定路径核对的公共机制，不把编辑器 UI 中的按钮、模型提供商列表或能力描述外推为每个宿主的默认行为。尤其是批准策略和 Checkpoint 都依赖有效配置，必须追到运行时值。

## 独特机制

Agent Runtime 在执行工具前合并基础工具策略与运行时策略覆盖。若策略把工具设为禁用，就生成 skipReason；若关闭自动批准，就通过 `requestToolApproval` 把会话、Agent、迭代、工具调用 ID、名称、输入和策略交给宿主。批准被拒绝时同样形成 skipReason，工具不会进入执行路径。Claim: cline.tools.denial-is-fail-closed。

这条批准路径具有明确的关闭失败行为：当工具要求批准但宿主没有配置批准回调时，返回 `approved: false`；批准回调抛出异常时也返回拒绝结果和原因。它避免了「界面失联后默认放行」这一类危险降级，但只约束这条 SDK 运行时路径。宿主若使用不同执行入口，仍需单独核对。

批准不是沙箱。用户或策略说「可以执行」只解决应用层授权，真实命令能够访问哪些文件、网络、凭证和外部服务，取决于进程身份、操作系统隔离和工具实现。批准提示中展示的参数也可能与最终执行参数存在转换，因此审计需要同时保存请求、决定和执行记录。

Checkpoint 解决的是另一件事。Core 配置将它定义为根 Agent Run 开始时捕获的可恢复工作区快照，内置实现基于 Git stash 与私有 ref，也允许调用方提供自定义创建函数。源码明确说明默认值为 false，即 Checkpoint 是选择启用的能力。Claim: cline.checkpoint-is-opt-in-snapshot。

即使启用，Checkpoint 的作用域主要是工作区文件。它可以帮助比较运行前后差异、恢复追踪和未追踪文件，但不能撤销已经发送的网络请求、数据库写入、云资源变更或外部消息。恢复文件也不自动恢复对话语义、模型端缓存或下游系统状态，所以回滚要和副作用补偿分开设计。

## 实现接缝

批准链的关键接缝位于策略归约与工具处理器之间。实现记录应同时保存基础策略、运行覆盖、最终 `enabled/autoApprove`、调用参数哈希、批准请求和 skipReason；处理器只接受没有 skipReason 且参数未变化的调用。批准回调缺失、拒绝或抛错都生成结构化拒绝观察，供 Agent 修正，而不是静默丢弃或落到默认允许。

Checkpoint 的接缝位于根 Agent Run 建立之前。只有有效配置启用时才创建快照，并把 ref、运行标识和工作树基线写入会话元数据；子迭代不应重复创建不受控快照。恢复动作要先列出将改变的追踪与未追踪文件，再执行 Git 层恢复，随后重新计算差异。Snapshot 与批准事件通过同一 Run ID 关联，但不合并为同一个安全状态。

教学实现可以用临时 Git 仓库和本地计数服务制造半恢复：工具同时修改文件并调用外部服务，之后恢复 Checkpoint。正确结果是文件回到基线、外部计数保持增加，并明确提示需要补偿。若系统把 UI 标为「全部回滚」，说明产品投影越过了恢复范围。

## 运行链

1. 模型产生工具调用，Runtime 先运行输入转换与前置钩子。
2. Runtime 合并工具的基础策略和当前覆盖，禁用策略直接阻断。
3. 需要批准时，宿主客户端收到带会话与调用归属的请求并返回决定。
4. 只有没有 skipReason 的调用进入真实工具执行器，结果再回到 Agent 迭代。
5. 若显式启用 Checkpoint，根运行开始前保存工作区快照并登记到会话元数据。
6. 失败后可选择比较或恢复文件；外部副作用由独立补偿与验证流程处理。

一条可审计轨迹至少要绑定工具调用 ID、输入哈希、策略来源、批准者或自动策略、最终执行参数、返回值和文件差异。Checkpoint 还要记录 ref、创建时间、runCount 与恢复操作。缺失批准事件不能解释为自动批准，缺失 Checkpoint 也不能解释为工作区无变化。

## 与一级主线的关系

Cline 作为扩展样本补充「编辑器宿主中的人机控制与恢复」机制。一级主线已经系统解释不同 Harness 的权限、会话和工具生命周期；本文不把 Cline 增设为全面主线，而是提供一个清楚案例，说明应用批准、OS 隔离、文件快照和任务评测是四个不同层次。

在统一评测链中，Runtime 轨迹和 Checkpoint 差异属于运行证据。Evaluator 应读取最终工作区、必要测试和禁止副作用；RewardAdapter 只有在评分语义完整时才把结果转给训练；候选选择与发布留出集继续独立。一次批准、一次成功执行或一次可恢复快照都不能单独成为奖励。

## 适用边界

关闭失败的批准回调适合嵌入式或多宿主 SDK，因为宿主失联时不会扩大执行权；它不能替代参数语义检查、最小进程权限和操作系统隔离。自动批准适合预先约束的低风险工具，危险命令、外发和不可逆操作仍需更窄策略与外部控制。

Git Checkpoint 适合受版本控制的工作区修改、差异预览和文件级恢复。数据库、远端 API、后台进程、项目外目录以及被忽略的大对象不在其天然事务范围。本文不覆盖所有 Cline 宿主和 UI，也不声称 Checkpoint 是完整会话恢复；选择该机制时必须把可逆范围和补偿责任展示给用户。

## 失败与限制

最常见的误判是把批准当成安全审查。用户可能看不到完整参数，策略可能过宽，工具实现可能在批准后扩展作用域。第二个误判是把 Checkpoint 默认存在；锁定配置明确默认关闭。第三个误判是认为恢复 Git 工作区能撤销所有影响，而外部 API、数据库和消息系统可能已经产生不可逆状态。

还要区分会话状态与任务正确性。宿主界面显示完成、Runtime 正常停止或所有工具都获准，只能说明生命周期没有在这些点失败。模型可能修改错文件、遗漏需求或通过删除测试来制造绿色结果，仍需独立验收。

## 验证方法

批准实验应构造同一个无副作用工具的三种策略：自动批准、要求批准后拒绝、要求批准但无回调。验证后两种都不调用工具处理器，并保存 skipReason。再让批准回调抛出异常，确认仍然关闭执行。实验需要固定锁定 Commit 和配置，不能只截取 UI。

Checkpoint 实验在临时 Git 仓库中准备追踪与未追踪文件，分别在关闭和启用配置下启动根运行。确认关闭时没有快照，启用时产生可比较 ref，并验证恢复只影响工作区。额外模拟一个外部副作用，证明 Git 恢复不会自动补偿它。

## 自检

### 问题 1

工具获批后是否说明安全？

**答案：** 不说明。批准是应用授权，仍需验证执行参数、进程权限和沙箱。

### 问题 2

Checkpoint 默认开启吗？

**答案：** 没有。锁定配置明确为选择启用。

### 问题 3

恢复快照能撤销 API 调用吗？

**答案：** 不能。它主要覆盖工作区文件，外部副作用需要补偿机制。

### 问题 4

Cline 为什么是扩展样本？

**答案：** 这里提炼的是批准与恢复分层，不承担对整个产品和所有宿主的一级全景分析。
