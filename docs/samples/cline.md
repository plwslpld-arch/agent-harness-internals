# Cline：工具批准与可恢复工作区

## 为什么值得单独看

Cline 这个扩展样本聚焦两个经常被混在一起的控制问题，一个是工具能不能执行，另一个是文件改动能不能恢复。前者由运行时工具策略、客户端批准回调和执行器共同决定，后者则交给可选的 Git Checkpoint 机制。只有把两条链分开，才不会因为「用户点了批准」就推断系统安全，也不会看到「可以回滚」便以为所有副作用都可逆。

当前锁定源码同时包含 SDK 化的 Agent Runtime、Core、Shared 类型与多种宿主表面，但本文只总结能够从锁定路径核对的公共机制，不会把编辑器 UI 里的按钮、模型提供商列表或能力描述外推成每个宿主的默认行为。批准策略和 Checkpoint 尤其依赖有效配置，所以必须一直追到运行时值。

## 两条不能混用的链：批准与 Checkpoint

Agent Runtime 会在执行工具前合并基础工具策略与运行时策略覆盖，如果最终策略把工具设为禁用，它就生成 skipReason。如果策略只是关闭自动批准，Runtime 会通过 `requestToolApproval` 把会话、Agent、迭代、工具调用 ID、名称、输入和策略交给宿主，而一旦批准被拒绝，同样会形成 skipReason，工具也就不会进入执行路径。

这条批准路径明确采用关闭失败行为，当工具要求批准而宿主没有配置批准回调时，它会返回 `approved: false`，批准回调抛出异常时也会返回拒绝结果和原因。这样可以避免「界面失联后默认放行」一类危险降级，不过它只约束这条 SDK 运行时路径，宿主如果使用别的执行入口，仍然需要单独核对。

批准不是沙箱——用户或策略给出的「可以执行」只解决应用层授权，真实命令最终能够访问哪些文件、网络、凭证与外部服务，仍取决于进程身份、操作系统隔离和工具实现。由于批准提示里展示的参数还可能在执行前经过转换，所以审计必须同时保存请求、决定和执行记录。

Checkpoint 解决的是另一件事，Core 配置把它定义为根 Agent Run 开始时捕获的可恢复工作区快照，内置实现基于 Git stash 与私有 ref，同时也允许调用方提供自定义创建函数。源码明确把默认值写成 false，因此 Checkpoint 是一项需要主动启用的能力。

即使已经启用，Checkpoint 的作用域仍主要落在工作区文件上，它可以帮助比较运行前后的差异，也能恢复追踪和未追踪文件，却无法撤销已经发出的网络请求、数据库写入、云资源变更或外部消息。恢复文件也不会自动恢复对话语义、模型端缓存和下游系统状态，所以回滚必须与副作用补偿分开设计。

## 从哪里开始读源码

可以从 [`Agent Runtime` 的工具策略与批准请求](https://github.com/cline/cline/blob/09ee9026393e681a4834d8acbf4d9d5fdfa8664a/sdk/packages/agents/src/agent-runtime.ts#L1744-L1808) 开始，重点记录 `policy.enabled`、`policy.autoApprove`、批准回调缺失、回调拒绝和回调异常这五条分支最终怎样形成 skipReason。接着查看后续执行函数，确认带有 skipReason 的调用确实不会到达工具处理器。

然后读 [`Checkpoint` 配置契约](https://github.com/cline/cline/blob/09ee9026393e681a4834d8acbf4d9d5fdfa8664a/sdk/packages/core/src/types/config.ts#L184-L218)，因为默认值、调用时机和自定义契约都写在这里。如果还要验证具体实现，就继续沿 `hooks/checkpoint-hooks.ts` 查看 Git 快照与私有 ref，并用相应的上游测试核对未追踪文件、重复运行和恢复行为。

## 把策略、执行和快照连起来

批准链的关键接缝位于策略归约与工具处理器之间，因此实现记录要同时保存基础策略、运行覆盖、最终 `enabled/autoApprove`、调用参数哈希、批准请求和 skipReason。处理器只应接收没有 skipReason 而且参数未变化的调用，批准回调缺失、明确拒绝或抛错时都要生成结构化的拒绝观察，让 Agent 有机会修正，而不是静默丢弃或退回默认允许。

Checkpoint 的接缝位于根 Agent Run 建立之前，只有有效配置启用时才会创建快照，并把 ref、运行标识和工作树基线写入会话元数据。子迭代不应重复创建不受控快照。恢复时要先列出将被改变的追踪与未追踪文件，再执行 Git 层恢复，随后重新计算差异，而 Snapshot 与批准事件虽然通过同一 Run ID 关联，却不能合并成一个笼统的安全状态。

教学实现可以利用临时 Git 仓库和本地计数服务制造一次半恢复，让工具同时修改文件并调用外部服务，之后再恢复 Checkpoint。正确结果应当是文件回到基线，外部计数却依然增加，并且系统明确提示还需要补偿。如果 UI 此时显示「全部回滚」，就说明产品表述越过了真实恢复范围。

## 沿一次受控编辑走完整链

1. 模型产生工具调用，Runtime 先运行输入转换与前置钩子。
2. Runtime 合并工具的基础策略和当前覆盖，禁用策略直接阻断。
3. 需要批准时，宿主客户端收到带会话与调用归属的请求并返回决定。
4. 只有没有 skipReason 的调用进入真实工具执行器，结果再回到 Agent 迭代。
5. 若显式启用 Checkpoint，根运行开始前保存工作区快照并登记到会话元数据。
6. 失败后可选择比较或恢复文件；外部副作用由独立补偿与验证流程处理。

一条可审计轨迹至少要绑定工具调用 ID、输入哈希、策略来源、批准者或自动策略、最终执行参数、返回值和文件差异，而 Checkpoint 还要另外记录 ref、创建时间、runCount 与恢复操作。轨迹里没有批准事件，不能解释成自动批准，同样，没有 Checkpoint 也不代表工作区没有变化。

## 它补充了六条主课程的什么

Cline 作为扩展样本，补充的是「编辑器宿主中的人机控制与恢复」机制，而一级主线已经系统解释了不同 Harness 的权限、会话和工具生命周期。本文不把 Cline 增设成一条全面主线，只用这个案例说明应用批准、OS 隔离、文件快照和任务评测分属四个层次。

Runtime 轨迹和 Checkpoint 差异都属于运行证据，因此 Evaluator 还要读取最终工作区、必要测试与禁止副作用，不能因为出现了一次批准、一次成功执行或一个可恢复快照，就单独判定任务正确。

## 什么时候值得采用

关闭失败的批准回调适合嵌入式或多宿主 SDK，因为宿主失联时不会扩大执行权，但它不能替代参数语义检查、最小进程权限和操作系统隔离。自动批准适合已经受到约束的低风险工具，危险命令、对外发送和不可逆操作仍需要更窄的策略与外部控制。

Git Checkpoint 适合处理受版本控制的工作区修改、差异预览和文件级恢复，但数据库、远端 API、后台进程、项目外目录以及被忽略的大对象都不在它天然覆盖的事务范围内。本文不覆盖所有 Cline 宿主和 UI，也不会把 Checkpoint 说成完整的会话恢复。选择这项机制时，必须让用户看清可逆范围和补偿责任。

## 最容易误判的地方

最常见的误判是把批准当成安全审查，因为用户可能看不到完整参数，策略可能划得太宽，工具实现也可能在批准后扩大作用域。另一个误判是以为 Checkpoint 默认存在，锁定配置却明确将它关闭。还有人会认为恢复 Git 工作区就能撤销所有影响，但外部 API、数据库和消息系统可能早已产生不可逆状态。

还要把会话状态与任务正确性分开，因为宿主界面显示完成、Runtime 正常停止或所有工具都获得批准，只能说明生命周期没有在这些点失败——模型仍可能改错文件、漏掉需求，甚至删除测试来制造绿色结果，所以独立验收不能省略。

## 怎样亲手核对

批准实验可以为同一个无副作用工具构造三种策略，分别是自动批准、要求批准后拒绝，以及要求批准但不提供回调。验证时要确认后两种策略都不会调用工具处理器，并保存各自的 skipReason，再让批准回调主动抛出异常，检查执行是否依然关闭。实验还要固定锁定 Commit 和配置，不能只截取 UI 作为证据。

Checkpoint 实验可以先在临时 Git 仓库中准备追踪文件和未追踪文件，再分别以关闭、启用两种配置启动根运行。关闭时应确认没有快照，启用时则要看到可比较的 ref，并验证恢复只影响工作区。最后再模拟一个外部副作用，用实际结果证明 Git 恢复不会自动补偿它。

## 读完后做四个判断

### 问题 1

工具获批后是否说明安全？

**答案：** 不说明。批准是应用授权，仍需验证执行参数、进程权限和沙箱。

### 问题 2

Checkpoint 默认开启吗？

**答案：** 没有。锁定配置明确为选择启用。

### 问题 3

恢复快照能撤销 API 调用吗？

**答案：** 不能。它主要覆盖工作区文件，外部副作用需要补偿机制。

### 问题 4

Cline 为什么是扩展样本？

**答案：** 这里提炼的是批准与恢复分层，不承担对整个产品和所有宿主的一级全景分析。
