# Qwen Code：Serve 回放与批准作用域

## 为什么值得单独看

Qwen Code 与 Gemini CLI 共享一些容易辨认的结构和概念，但当前锁定仓库已经包含规模可观的 Serve、ACP Bridge、Daemon、SDK 与多客户端会话能力。因此，本专题不考证历史谱系，也不从相似目录推断行为等价，而是只选择当前源码中能直接核对的两个独特机制：一个按轮次压缩事件回放，另一个通过 Serve Bridge 限制危险批准模式。

这两个机制说明，当 Agent Harness 扩展到长驻服务和多个客户端后，就会遇到单进程 CLI 中并不突出的新问题，流式事件需要在内存占用与可恢复性之间取舍，而会话批准模式可能被远端工具改变，因此必须限制它的作用域和持久化范围。它们补充的是六条一级主线中的协议与会话视角，并不会把 Qwen Code 升为新的综合主线。

## 轮次回放压缩与批准作用域

`TurnBoundaryCompactionEngine` 会在 `turn_complete` 或 `turn_error` 处折叠当前轮次积累的事件，其中连续文本和思考块被合并，工具调用序列归约到最终状态，瞬态信号被丢弃，而不同事件类型的相对顺序依然保留。这样一来，回放日志的规模就会随对话轮次数增长，而不是跟着每个流式令牌一起增长。

压缩虽然降低了内存与回放成本，却也改变了证据的颗粒度，因为被丢弃的瞬态信号无法从压缩日志复原，工具调用只保留归约状态时也可能丢失中间转移。源码还设置了回放字节、事件数、Journal 增长和截断锚点等限制，这意味着长会话仍可能发生窗口淘汰。旧记录会消失——所以压缩日志适合用于客户端恢复和界面展示，但不能自动替代高保真审计轨迹。

Serve Bridge 还暴露了改变会话批准模式的工具，它虽然接受 plan、default、auto-edit、auto 与 yolo 五种值，但在 `allowGlobalScope` 未开启时，会明确拒绝 auto-edit、auto、yolo 和持久化变更。只有显式开放全局作用域后，请求才会被交给 DaemonClient。

这道门禁控制的是远端 Bridge 表面上的风险扩张，它可以防止普通桥接调用悄然把会话切换到更自动的执行模式，也可以阻止变化被写入工作区设置并影响后续会话。但它并不等于完整的安全边界，因为直接 CLI、其他 API 表面、工具本身和沙箱仍有各自的策略，而开放全局作用域后，更需记录调用者、会话和持久化范围。

## 从哪里开始读源码

从 [`TurnBoundaryCompactionEngine`](https://github.com/QwenLM/qwen-code/blob/4d3f9ff5719157fda5e8b135ed5bc362d925bcf0/packages/acp-bridge/src/compactionEngine.ts#L232-L301) 阅读类说明、预算字段、回放片段和截断锚点。继续到 ingest、轮次终止与 snapshot 时，应记录哪些事件被合并、哪些被丢弃、何时生成历史截断标记，以及客户端如何取得之前的记录。

批准作用域从 [`workspaceWrite` 的模式变更工具](https://github.com/QwenLM/qwen-code/blob/4d3f9ff5719157fda5e8b135ed5bc362d925bcf0/packages/sdk-typescript/src/daemon-mcp/serve-bridge/tools/workspaceWrite.ts#L81-L115) 阅读。重点区分「允许的枚举值」「默认作用域允许的值」「是否持久化」和「最终会话 ID」。工具描述列出一种模式，不代表默认门禁会放行它。

## 把实时事件、回放窗口和会话控制连起来

实时 Journal 与回放片段的接缝发生在轮次完成或错误边界。引擎在轮次内接收增量事件，按类型合并文本与思考、归约工具状态并保留跨类型顺序，随后才把片段放入受字节和事件预算限制的窗口。实现要记录压缩前后数量、丢弃类型、截断锚点和当前 Cursor，客户端才能知道恢复到的是有损投影而非完整 Trace。

回放窗口与多客户端的接缝是快照加增量。客户端先取得窗口快照和锚点，再订阅新事件，而断线重连时使用 Cursor 去重，如果所需位置已被淘汰，就会收到显式截断状态。高风险工具的原始调用、批准和结果应写入独立不可变审计流，不能依赖为 UI 优化的压缩 Journal。

Serve Bridge 与会话控制 API 的接缝由 `allowGlobalScope` 守卫。请求先校验模式、持久化意图和作用域，默认只允许较窄变化，即使开放全局作用域，仍需绑定调用者、目标 Session、旧值、新值和有效期。模式变化只改变应用批准策略——工具执行器与 OS 隔离继续独立判断。

## 沿一次长驻会话走完整链

1. Agent 运行产生文本、思考、工具调用、权限与轮次终止等流式事件。
2. ACP Bridge 在轮次进行中维护实时 Journal，并在完成或错误边界执行折叠。
3. 压缩片段进入受字节与事件预算约束的回放窗口，必要时保留截断锚点。
4. 终端、网页、协议客户端或 SDK 按会话订阅、重连并读取回放状态。
5. 若客户端通过 Serve Bridge 改批准模式，先经过全局作用域门禁，再调用会话控制 API。
6. 独立评测读取真实产物和所需原始证据，不把回放完成或批准变更当作任务通过。

为了保证可追溯，应当把 session ID、事件 ID、轮次边界、压缩前后数量、截断计数、记录锚点、客户端订阅位置和批准模式变化放在同一条血缘中。如果任务风险较高，还应另行保存不可变的原始工具调用与结果，因为客户端回放日志本就有意做了有损优化。

## 它补充了六条主课程的什么

Gemini CLI 一级主线只按锁定 Gemini 源码解释其配置、调度、工具和会话，而 Qwen Code 样本按自己的锁定 Commit 解释 Serve 扩展。两者可以共享比较维度，却不能因为包名、目录或早期关系就互相代替证据。任何「同源」描述都只用于定位，行为结论必须落到各自源码和测试。

对其他主线，这个样本提出了两个通用问题，一个是长驻 Harness 向多个客户端提供会话时如何限界回放，另一个是权限模式能否被协议表面远程扩大。Codex、Claude、pi、OpenCode 和 DeepSeek Harness 需要按各自实现回答，不能直接套用 Qwen Code 的字段或默认值。

## 什么时候值得采用

轮次边界压缩适合这样的长驻服务：事件量远大于轮次数，客户端需要快速重连，而 UI 并不要求逐令牌审计。但在调试流式解析、合规取证或操作高风险工具时，就需要并行保留更高保真的证据。窗口预算越小，恢复成本与不可见历史就越大，所以应当按任务风险配置。

Bridge 作用域门禁适合防止普通远端工具扩大自动批准和持久化设置，但它只能保护这一入口，所以直接 CLI、其他 SDK、配置文件与组织策略仍需分别核对。本文不会因为 Qwen Code 与 Gemini CLI 结构相似就外推语义，也不评价 Qwen Code 的全部产品表面。真正可迁移的是对有损回放的明确声明、快照 Cursor 和权限扩大审计。

## 最容易误判的地方

第一类风险是把压缩回放当成完整审计，但保留相对顺序并不代表所有中间事件也被保留，而截断窗口还可能淘汰旧轮次。第二类风险是把 Bridge 的默认门禁当作全系统策略，然而它只覆盖这条 Daemon MCP Serve Bridge 工具路径，其他入口仍需单独检查。

第三类风险是把同源理解为等价，而即便两个仓库存在共同结构，独立演进也会改变配置优先级、工具策略、协议事件和恢复语义。如果评测混用两个 Harness 的默认值，可复现性就会被破坏。批准模式也只是应用层控制，不能替代容器、进程权限、网络和凭证隔离。

## 怎样亲手核对

回放实验可以先构造一个包含大量文本分片、思考分片和工具状态变化的轮次，然后在完成边界前后比较事件数与顺序，确认同类片段已合并、工具状态已归约，同时不同类型的相对顺序仍然保持。随后再降低窗口预算来触发截断，验证客户端确实收到了明确标记和分页锚点。

批准实验应在默认 `allowGlobalScope=false` 时分别请求 plan、auto-edit、auto、yolo 与持久化 default，先确认危险模式和持久化都被拒绝，显式开放全局作用域后，再验证请求确实到达了指定会话。开放门禁不等于已经安全批准，所以实验仍要在受控工具和隔离环境中运行。

## 读完后做四个判断

### 问题 1

回放压缩是否无损？

**答案：** 不是。它合并片段、归约工具状态并丢弃瞬态信号。

### 问题 2

默认 Bridge 能否切到 yolo？

**答案：** 不能，除非显式开放全局作用域。

### 问题 3

该门禁是否覆盖所有 Qwen Code 入口？

**答案：** 不覆盖，本文结论只描述 Serve Bridge 工具路径。

### 问题 4

与 Gemini CLI 结构相似是否说明行为一致？

**答案：** 不说明，必须分别锁定源码、配置与运行证据。
