# 从这里开始

这是理解整座知识库的入口，职责远大于项目名单索引。读完本页，你应该能判断 Agent Harness 的边界、六条主线为什么必须独立展开、Eval 为什么属于横切验证能力，以及一篇文章达到什么状态后才值得进入正式导航。

## 这个入口解决什么

直接阅读某个项目的目录，很容易把文件结构误当成系统结构：一个名为 `tools` 的目录不一定负责工具执行，一个名为 `session` 的包也不一定拥有会话生命周期。这里先建立共同概念，再把概念映射回每个锁定版本中的真实实现。映射失败时保留差异，不强迫六个项目使用同一套术语。

另一个常见误区是把模型、Agent Harness、运行环境和 Eval 压成一个分数。模型生成候选内容，Harness 决定上下文、工具、权限、循环和持久化，环境决定可见文件与可用资源，Eval 决定任务、产物和判分口径。任何一层变化都可能改变结果；只有把四层分别记录，比较才有归因价值。

本仓库因此采用一条主线和一条横切能力。主线研究 Agent Harness 如何把目标变成行动；横切能力研究这些行动怎样留下证据、怎样被评分、怎样进入反馈和发布决策。两者会在每条项目课程中相遇，但不会被写成互不相干的两套百科。

## 概念地图

![Agent Harness 主线与 Eval 横切验证关系图](../assets/diagrams/start/agent-harness-scope.svg)

上半部分是任务执行主线。用户目标先进入上下文装配，随后形成模型请求；模型返回的内容或工具意图经过参数校验、权限策略和真实执行，结果被写回会话，再由终止条件决定继续循环还是生成补丁、回复、轨迹等产物。不同 Harness 会合并或拆分这些阶段，但都必须回答同一组控制问题。

下半部分不是第二个 Agent。Eval 固定任务和环境，以 Trial 为统计单位管理 Attempt，收集 Trace 与 Artifact，再把产物交给 Scorer。Feedback 可以回到数据整理、训练奖励或产品改进，但训练反馈、Checkpoint 选择和独立发布评测必须保持可说明的隔离关系。

图中的虚线只表示证据采集，不表示 Eval 接管工具执行。反过来也一样：Harness 能记录轨迹，不等于它已经定义了统计上有效的评测。执行能力和验证能力需要连接，也需要分工。

每条主线都会从真实入口开始，沿一次完整任务追到终止或恢复，再单独解释扩展与 Eval 接入。这样做比先写总矩阵更慢，却能避免把同名概念误判为相同实现，也能让横向比较中的每一个单元格回到各方独立证据。

Claude 主线采用双边界：Claude Code 的公开行为只引用官方文档，不能用 Agent SDK 源码替代；Python 和 TypeScript SDK 的实现事实分别绑定锁定源码与许可证。看不见的闭源内部机制标成 `unknown`，不以经验猜测填空。

扩展样本包括 mini-swe-agent、OpenHands、Cline、goose、Aider 和 Qwen Code。它们只用于补充独特机制，不在六条主线完成前进入正式导航，也不会为了数量复制一套较浅的同构课程。

如果你准备实现或改造 Harness，选一条与你技术栈最接近的主线从头读完，不要只抽取功能表。完整跟踪真实输入、状态变化、工具结果、失败路径与终止条件后，再去横向比较其他实现；这能减少把表面 API 当成系统语义的风险。

如果你负责质量、发布或评测，沿 Trial、Attempt、Trace、Artifact、Scorer 和 Feedback 阅读。重点检查统计单位是否稳定、基础设施重试是否改变分母、产品失败是否被重试成通过，以及训练数据和独立发布集是否泄漏。

如果你负责产品、安全或平台治理，优先观察权限提示何时出现、默认策略是什么、Sandbox 能限制哪些资源、Hook 能否绕过核心策略、会话恢复会不会重复副作用，以及不同客户端是否共享同一服务端状态。

正式文章开放后，推荐按以下步骤阅读：

1. 从本文确认概念和证据口径。
2. 完成共同基础，理解跨项目都要回答的问题。
3. 选择一条一级主线，沿端到端任务链完整阅读。
4. 用实验文章复核关键行为，再阅读横向比较与角色路径。
5. 最后查看扩展样本，只提取它们相对六条主线真正新增的机制。

## 状态与导航

`outline` 只有提纲和待核证据，`draft` 已有正文但尚未达标，二者都不会进入正式导航。`reviewed` 表示内容、来源、图示和边界已经完成对抗复核；`verified` 还要求相关实验可复现。这两种状态才会成为课程链接。

`stale` 用来保护读者免受过期证据误导，它不评价文章的永久质量。当上游 Commit、文档或实验环境发生漂移，页面就应退出正式导航，直到重新绑定来源并复核受影响结论。状态表可以继续显示它，以便读者知道缺口，却不能把它当成仍然有效的课程。

当前正式导航包含这个总入口、六篇共同基础和 DSH 九篇课程。其余五条主线的状态会公开显示，但在达到 `reviewed` 前不提供课程链接。文件存在、篇幅很长或测试通过，都不能绕过这条发布规则。

## 证据方法

来源首先由机器清单锁定仓库、Commit 和许可证。正文中的源码锚点必须在对应 Checkout 中真实存在；关键公开结论还进入结论注册表，记录能力状态、证据等级、限定条件和反例。图示如果概括了结论，也必须登记来源关系，并在上游漂移后一起失效。

一项结论只有在读者能够从文章中的具体表述回到结论注册表，再沿来源 ID、锁定 Commit、仓库相对路径、准确行号和对应上游测试逐层核对，并在声明存在运行证据时找到完整输入、环境、命令、产物与失败记录，才形成闭合的验证链；中间任何一段无法复核，都必须降低等级或明确标成未知。

链路不能跳步。

证据等级从 A 到 U。A 同时需要源码、上游测试和本地实验；B 需要源码与测试；C 由源码或官方文档直接支持；D 是明确写出的推断；U 表示未知、冲突或不适用。等级表达证据形态，不是给项目打分，同一项目可以在不同结论上拥有不同等级。

能力状态使用 `default`、`optional`、`extension`、`external`、`absent`、`unknown` 和 `not-applicable`。它们把默认行为、配置能力、扩展能力和外部依赖分开，避免一个含糊的「支持」掩盖实际使用条件。

阶段复核记录承诺、证据、发现、处理和最终命令。高严重度发现没有解决时，阶段不能标记通过。当前复核由同一执行流程完成，因此只证明已执行明确的反例检查，不冒充来自其他模型或独立团队的外部审计。

复核也有边界。

## 本地验证

日常完整检查使用 Node 24，不调用 NVM。先准备默认 `core` 来源，再运行聚合门禁：

```bash
npm run bootstrap
npm run check
```

需要检查扩展样本和外部评测参照时，可以显式选择全部来源：

```bash
node scripts/verify-sources.mjs --profile all
```

聚合检查覆盖来源锁、文章元数据、结论注册表、正式导航、内容深度、中文视觉、阶段复核、源码锚点、许可证、链接、敏感信息与单元测试。它能发现仓库内部不一致，却不能替代真实环境中的安全评估、统计设计或发布审批。

## 边界

仓库只使用公开、可授权的源码、上游测试、官方文档和明确记录的实验。泄露 Prompt、私有会话、来源不明的转储和未授权逆向材料不进入证据链。Claude 等闭源产品只能在公开契约范围内表述，不能因为 SDK 存在就声称掌握产品内部实现。

课程和实验用于理解机制与复核结论，不证明生产就绪、发布授权或维护者的个人能力。第三方 Benchmark 结果会写明来源、日期、口径和是否复跑；没有复跑的结果只能作为外部背景，不能改写成本仓库自己的成绩。

## 自检

### 问题 1

为什么 Eval 不作为与 Agent Harness 并列的第二条课程主线？

**答案：** 因为仓库的核心对象是把模型变成可行动 Agent 的运行系统；Eval 负责固定任务、收集产物和执行评分，应在每条 Harness 主线中验证真实执行，而不是脱离执行系统另写一套同等规模的百科。

### 问题 2

一个已经存在且很长的文件为什么仍可能不进入正式导航？

**答案：** 正式导航只接受 `reviewed` 和 `verified`。篇幅不能替代来源绑定、结构深度、中文图示、边界说明和对抗复核；上游漂移后的长文也必须先标成 `stale`。

### 问题 3

源码、上游测试和本地实验分别解决什么问题？

**答案：** 源码说明锁定版本写了什么，上游测试说明维护者用什么行为约束实现，本地实验说明指定输入和环境下能否复现。三者共同存在时证据最强，但仍不能外推为所有平台和生产场景的发布证明。
