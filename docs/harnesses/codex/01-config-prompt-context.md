# Codex 配置、提示与上下文

## 读者会得到什么

本篇回答一个经常被压成一句话的问题：Codex 到底把什么交给模型？答案不是「配置文件加用户消息」。持久配置、命令行覆盖、线程设置、模型默认指令、开发者指令、AGENTS.md、权限与环境说明、扩展上下文片段、历史投影和当前用户输入在不同阶段进入；其中有些属于稳定前缀，有些随工作目录或轮次变化，还有些只在功能开启并满足大小、模态或标记约束时可见。

读完后，你应能区分三件事：磁盘上写了什么、当前线程解析出的有效配置是什么、某次模型请求实际包含什么。你也应能解释为什么切换工作目录会追加新的 AGENTS 指令，为什么线程设置改变不必改变提示缓存键，以及为什么 Context Fragment 是受角色、标记、分类、历史正规化和上下文窗口共同约束的输入片段。

本篇只对锁定提交作结论。上游测试使用模拟 Responses 服务；它能核对请求体布局和缓存键，不是线上缓存命中率或成本实验。

## 核心概念

配置、提示与上下文位于三条不同的数据链上。配置链决定运行参数，提示链决定固定指导，历史链决定本次请求携带哪些已经发生的对话和工具结果。它们最终在 Responses 请求相遇，却不能因出现在同一个 JSON 中就视为同一种数据。

| 概念 | 生命周期 | 典型来源 | 直接决定 |
|---|---|---|---|
| 持久配置 | 跨线程或项目 | 配置文件、环境、宿主 | 候选模型、功能与默认值 |
| 有效配置 | 当前线程或 Turn | 分层合并、线程设置 | 本次运行实际采用的参数 |
| 基础指令 | 模型与线程级 | 模型默认、指令文件、内联配置 | 稳定行为前缀 |
| 开发者指令 | 线程或宿主级 | 配置与调用方覆盖 | 任务之上的实现约束 |
| 项目指令 | 工作目录范围 | AGENTS.md、后备文件 | 当前目录树的本地规则 |
| Context Fragment | 功能或扩展级 | 世界状态、扩展服务 | 有角色和标记的动态片段 |
| 原始历史 | Session 生命周期 | 用户、助手、工具事件 | 可恢复事实与审计 |
| 模型可见历史 | 单次采样 | 正规化、模态过滤、压缩 | 本次请求的 input 项 |

「来源、有效值、模型可见值」是最重要的三分法。磁盘配置只是一组候选输入；加载器按字段合并后得到线程有效配置；Prompt 构造器再选择其中需要显式呈现给模型的部分。审批策略可能影响工具执行，却不一定以原字符串进入基础指令。复核者必须分别保存三份快照。

稳定前缀指相邻请求中保持字节布局稳定、可能被服务端复用的起始部分。它通常包括基础指令、稳定工具规格和早期历史；当前目录、权限说明、用户消息或新工具结果会使后缀变化。缓存键是客户端提供的身份提示，不是命中证明；真正命中还依赖服务端、模型和过期策略。

项目指令具有目录作用域。切换工作目录后，旧 Turn 的历史仍应保留当时模型看见的 AGENTS 包装项，新目录规则作为当前更新进入后续请求。若直接覆盖旧项，历史会失去解释力；若仍让旧规则支配新目录，又会违反当前作用域。保存旧事实与应用新约束需要同时成立。

Context Fragment 是结构化注入接缝。它声明角色、内容分类、是否独立成消息以及起止标记，随后接受历史正规化和模型模态限制。片段生成成功只证明候选内容存在；只有最终请求体能证明这次采样真正看见了它。

上下文预算还引入取舍顺序。基础指令、当前用户目标、未结算工具关系与项目规则通常具有不同保留优先级；压缩或模态过滤必须保持工具调用与结果成对，不能为了塞入新片段留下孤立结果。预算决定可见投影，不应删除原始 Session 中的证据。

配置里含有路径、凭据引用和网络端点时，provenance 也属于安全数据。公开记录应保存来源类型、字段是否存在和不可逆哈希，不复制秘密值；模型请求捕获同样需要脱敏。可核对并不要求泄露内容，而是要求审阅者能证明某项配置参与了合并。

## 为什么这样设计

第一，逐字段配置合并允许宿主只覆盖必要选项。一次临时运行可以更换模型而保留项目文档和安全默认值；若每个覆盖都替换整份配置，小改动会意外清除其他边界。双层可选值还能表达「不覆盖」与「显式恢复默认」的差别。

第二，原始历史与模型投影分离，使审计完整性和上下文预算可以兼得。Session 保存发生过的消息与工具关系，投影器按当前模型支持的模态、窗口和压缩策略生成请求。更换模型不会要求篡改旧历史，恢复也能重建不同投影。

第三，项目指令按目录追加更新，是为了保持时间与作用域。模型上一轮行为应能由当时规则解释，下一轮又必须遵循新目录规则。把每个指令项带上来源和作用域，能够诊断「规则没发现」「规则已截断」「规则被更新」三类不同问题。

第四，把轮次动态信息放在稳定前缀之后，可以减少无意义的缓存失效。安全语义仍由当前有效配置与执行层决定，缓存布局只优化重复输入；两者若冲突，应优先保证正确可见性，而不是保住键。

第五，扩展片段使用显式标记和分类，便于正规化、替换与限制注入。无结构字符串拼接很难知道来自哪个扩展，也难在内容超限或功能关闭时准确移除。结构化边界同时为提示注入审计提供来源线索。

这些设计共同支持可解释差分：当两次回答不同，研究者可以先比较有效配置，再比较模型可见请求，最后比较 Provider 输出。若三层快照混在一起，只能看到最终文本变化，无法归因于规则发现、历史压缩、模型设置还是随机采样。

## 实现思路

教学原型可以将请求构造拆成三步纯函数与一个观察器。它不复刻 Codex 内部 Rust 类型，只用于理解输入如何从来源走向最终请求。

1. **收集来源。** 读取持久配置、调用方覆盖、线程设置、当前工作目录和模型信息；每个字段同时记录值与 provenance。
2. **解析有效配置。** 按字段定义合并优先级，验证路径、空字符串、字节上限和 Feature 条件；拒绝用整份对象覆盖模拟所有字段。
3. **发现指导。** 选择基础和开发者指令，沿目录链发现项目文档，生成带作用域和内容哈希的 Context Fragment。
4. **正规化历史。** 保留原始历史副本，根据模型模态、压缩边界和独立消息要求生成可见项；任何丢弃都写原因。
5. **布局请求。** 先放稳定指令与工具规格，再放正规化历史、当前环境更新和用户输入；计算缓存身份并保存字节级前缀摘要。
6. **捕获实际发送体。** 在模型客户端边界记录脱敏请求、模型和响应元数据，只有这一层用于回答「本次看见什么」。

```text
sources = collect(config_file, cli_overrides, thread_settings, cwd)
effective = merge_per_field(sources)
instructions = resolve_instructions(effective, model, cwd)
visible_history = normalize(raw_history, model.modalities, context_budget)
request = layout(instructions, tool_schema, visible_history, current_input)
observe_redacted(request, provenance, prefix_hash)
```

原型应为每个可见项保留 `source`、`scope`、`introducedAtTurn` 和 `contentHash`。这些字段可以放在旁路证据中，不必全部发送给模型。切换目录时，历史项保持原哈希，新项目指令获得新的作用域；这样能同时检查历史一致性和当前有效性。

缓存验证采用两类差分：只改变动态后缀时，断言旧请求前缀仍是新请求前缀；改变基础指令、工具 Schema 或模型时，断言差异从预期位置开始。测试不声称费用下降，只报告布局是否具有复用条件。

还要为历史正规化生成机器报告：每个原始项对应 kept、transformed 或 dropped，并附原因和目标索引。工具调用与结果若被拆散，构造器应直接失败；未知模态若被删除，要留下可观察告警。这样上下文超限时不会只剩一个难以复查的短请求。

字段合并测试使用表驱动方式覆盖缺省、显式空值、路径读取失败和调用方覆盖。每个字段的期望结果同时断言 provenance，避免值碰巧相同却来自错误层。对路径类指令还要冻结读取时点，否则文件在 Thread 创建与 Turn 采样之间变化会造成不可复现输入。

## 贯穿案例

设定两轮仓库任务。第一轮在模块甲询问「解释当前解析逻辑」，第二轮切换到模块乙并要求「修改测试」。两个目录拥有不同 AGENTS 规则，第二轮同时把权限从只读改为工作区可写，但保持模型和基础工具规格不变。

1. **冻结来源。** 保存配置文件、线程创建覆盖、两份 AGENTS 的路径与哈希，以及初始工作目录；敏感配置只保存存在性。
2. **构造第一轮。** 有效配置选择只读权限，发现模块甲规则；请求包含基础指令、工具 Schema、项目指令和第一条用户消息。
3. **提交目录切换。** 第二轮线程设置更新 cwd 与权限。加载器发现模块乙规则，但不删除历史中模块甲的旧包装项。
4. **生成第二轮请求。** 正规化历史保留第一轮消息，追加模块乙规则、当前权限环境和第二条用户消息；稳定前缀仍与第一轮对齐到预期边界。
5. **对抗验证。** 故意让模块乙 AGENTS 超过字节上限，再关闭项目文档功能，分别观察截断或缺失；任何结果都必须在 provenance 中说明。
6. **任务评分。** 独立 Scorer 检查修改是否只触及模块乙，不能仅凭请求含有新规则就判通过。

```json
{"turn":1,"cwd":"模块甲","projectInstruction":"hash-a","permission":"只读","cacheKey":"线程键"}
```

```json
{"turn":2,"cwd":"模块乙","visibleProjectInstructions":["hash-a","hash-b"],"permission":"工作区可写","cacheKey":"线程键"}
```

如果第二轮只出现 `hash-b`，历史解释链断裂；如果模型仍只应用 `hash-a`，当前目录约束错误；如果缓存键相同但前缀已从开头变化，缓存身份与布局不一致。这三个失败分别属于历史投影、作用域应用和缓存构造，不能合成「提示错误」。

案例最后保存脱敏请求体、字段 provenance、正规化报告和工作区产物。由此可以回答模型看到了什么、为什么看到、哪些候选内容未进入请求，以及实际修改是否满足任务，四种结论不会互相替代。

再加入一次模型切换：第三轮改用不支持图像输入的模型，原始历史中的截图仍保留，模型可见投影将其删除或替换成受支持描述，并在正规化报告中注明原因。若系统为了新模型直接改写历史，随后切回原模型也无法恢复证据，这应被测试阻断。

安全反例让命令行覆盖把审批设为永不询问，但执行层仍处于只读 Sandbox。请求体可以说明当前环境，却不能凭该说明获得写权限；真正写入仍由执行层拒绝。它证明 Prompt 可见的安全描述与操作系统强制边界需要一起复核。

## 真实输入与输出

### 输入

上游 `model_visible_layout.rs` 创建两个工作目录，并分别写入不同的 AGENTS.md：

```text
目录一：Turn one agents instructions.
目录二：Turn two agents instructions.
```

第一次 Turn 的用户输入是 `first turn in agents_one`，线程环境选择目录一；第二次输入是 `second turn in agents_two`，环境切换到目录二。两轮都使用只读权限配置和永不询问审批，模型响应则由确定性测试服务给出。

### 输出

测试捕获两次模型请求。第一次请求包含一份来自目录一的 AGENTS 包装项；第二次请求保留原指令项，同时追加目录二对应的替换项：

```text
第一次请求中的 AGENTS 指令包装项数量：1
第二次请求中的 AGENTS 指令包装项数量：2
```

这不是简单「用新字符串覆盖旧字符串」。历史需要保留当时模型看见的上下文边界，同时把当前工作目录的指令更新注入后续请求。另一个 `prompt_caching.rs` 测试则在两轮之间改变权限配置与推理设置，却断言提示缓存键保持相同，并检查第一轮输入前缀仍是第二轮的完整前缀；这证明某些轮次变化可以放在稳定前缀之后，而不是每次重建全部缓存身份。

## 调用链

![Codex 配置来源、有效线程设置、稳定提示前缀、动态上下文片段和模型可见请求的中文数据流图](../../../assets/diagrams/codex/01-config-prompt-context.svg)

Claim: codex.config.layered-and-thread-scoped

Claim: codex.context.fragments-are-bounded

1. 配置加载器读取持久配置结构，解析模型、基础指令文件、开发者指令、项目文档大小、功能开关和其他选项；命令行或宿主覆盖与配置值按字段合并，空字符串和无效路径会在解析边界处理。
2. Thread 创建时保存初始有效配置；每次 Turn 还可通过线程设置覆盖模型、推理强度、协作模式、环境、审批与权限。持久配置不是本轮配置的唯一来源。
3. Session 根据模型信息和有效配置选择基础指令；项目文档发现逻辑在当前工作目录链上读取 AGENTS.md 或配置的后备文件，并受 `project_doc_max_bytes` 限制。
4. 世界状态与扩展可以贡献上下文片段。每个片段拥有响应角色、稳定分类、可选起止标记和正文，并决定是否必须作为独立消息记录；实现者必须自行处理标记与正文间空白。
5. 历史管理器记录可用于接口的响应项，生成模型输入前会正规化历史，并按模型输入模态剥离不支持的图像、音频或工具输出内容。原始历史与模型可见投影不能视为同一个数组。
6. Prompt 构造器将基础指令与正规化输入交给模型客户端。稳定前缀和缓存键可以跨轮复用，轮次特有的权限、环境、AGENTS 更新和用户输入则按布局进入请求。
7. Responses 请求体才是「模型这次实际看见什么」的直接证据。配置文件、发现到的文档或扩展已安装，只能证明候选来源存在。

## 失败与限制

第一，配置优先级是逐字段的，不能用一句「命令行总是最高」替代源码核对。某些字段使用双层可选值表达「不覆盖、显式恢复默认、指定新值」，Feature、Provider 和宿主加载器也可能引入额外约束。要回答具体字段，必须追到该字段的解析分支。

第二，AGENTS 发现依赖有效工作目录、目录链、大小上限和后备文件名。文件存在但位于错误目录、超过截断上限、读取失败或项目文档功能被禁用时，模型可见结果都会不同。切换目录后保留旧项是历史一致性设计，不表示旧规则仍然支配新目录。

第三，上下文片段不是无限的隐藏系统提示。它有角色和内容分类，可能需要独立消息，标记可能用于识别和替换；最终还受历史正规化、模态支持、压缩和上下文窗口限制。扩展返回一个片段也不能证明它已出现在请求中。

第四，缓存键恒定不等于一定命中缓存。测试只证明锁定请求构造保持键与前缀关系；服务端是否接受、缓存是否过期、账号或模型是否支持、网络层是否改变请求，都超出该测试范围。缓存优化也不能以隐藏错误配置为代价。

第五，模型可见请求不是完整运行状态。审批策略、文件系统权限和环境连接可能以专门片段、工具规格或服务端元数据表达；外部秘密不应为了「可见性」无边界复制进 Prompt。验证应同时检查请求体和真实安全执行层。

配置存在不等于模型看见。

## 验证方法

先锁定配置来源：记录持久配置、命令行覆盖、宿主 Loader 覆盖、线程设置、当前工作目录和模型标识；对每个关键字段写出最终值与来源。不要从单份配置文件推断整个 Session。

再捕获模型请求：使用确定性模拟服务运行两轮，第一轮固定目录与 AGENTS，第二轮切换目录或线程设置。逐项比较顶层 instructions、input 数组、工具规格、权限与环境片段、用户消息以及提示缓存键；敏感值只记录存在性和哈希，不写入公开证据。

然后做边界注入：让 AGENTS 缺失、超大、位于父目录、使用后备文件名或在两轮间变化；让扩展片段使用空标记、错误空白、独立消息和不同内容分类；让模型不支持图像或音频。检查历史原始项、正规化后的模型输入和 Rollout 记录是否符合各自契约。

最后检查缓存：保持基础前缀不变，只改变明确属于轮次尾部的设置，确认键和前缀；再改变基础指令、模型或稳定工具规格，确认请求差异不会被错误吞掉。即使本地结构通过，也只能报告「具备缓存命中可能」，不能报告真实服务命中率。

## 自检

### 问题 1

为什么找到 AGENTS.md 还不能断言模型读到了它？

**答案：** 还要核对有效工作目录、目录发现、字节上限、功能配置、历史注入和最终请求体。文件存在只是候选来源证据。

### 问题 2

第二轮请求为什么可能同时出现旧 AGENTS 项和新 AGENTS 项？

**答案：** 历史保留第一轮真实可见上下文，新工作目录的规则作为更新追加；这样能解释前一轮行为，又给当前轮提供新边界，不是简单改写过去。

### 问题 3

提示缓存键在两轮间相同，能否证明节省了费用？

**答案：** 不能。它只证明请求构造保留了键和稳定前缀关系；真实缓存支持、命中、过期、计费和服务端策略需要独立线上观测。

### 问题 4

Context Fragment 与普通用户消息有什么关键差别？

**答案：** 片段由扩展或世界状态生成，显式拥有角色、内容分类、标记和独立消息要求，并经过历史正规化；它不是可以无限拼接、无来源的隐藏文本。
