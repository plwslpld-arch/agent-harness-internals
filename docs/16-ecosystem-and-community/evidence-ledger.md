# 生态与社区证据账本方法

## 证据等级

| 等级 | 例子 | 可以支持 | 不能单独支持 |
| --- | --- | --- | --- |
| A 官方可验证 | 源码、tag、package metadata、官方文档/API | 发布事实、实现与声明 | 真实采用、长期稳定性 |
| B 可复现实测 | 锁定 SHA/config 的运行记录、轨迹、benchmark | 特定组合下的行为 | 所有平台/版本的普遍结论 |
| C 独立使用证据 | 可核验团队案例、公开插件、含环境的 bug report | 使用场景、摩擦点 | 市场规模、无偏满意度 |
| D 社区讨论 | Discussions、Reddit、HN、中文社区 | 问题发现、舆情主题 | 能力真伪、代表性需求 |
| E 热度代理 | star、fork、浏览量、下载量 | 关注或获取 | 活跃使用、留存、商业价值 |
| F 推断 | 基于多源事实的分析 | 待验证假设 | 已确认事实 |

## 每条记录字段

```yaml
id: community-YYYYMMDD-NNN
canonical_url: https://...
publisher: ...
published_at: ...
captured_at: ...
evidence_class: D
content_hash_or_snapshot: ...
claim_supported: ...
claim_not_supported: ...
affected_version_or_sha: ...
conflicts: []
license_and_retention: link-only
reviewer: ...
```

只保留合法的短引文或摘要；删除帖子也要保留“已无法复核”的状态，而不是继续当活证据。

## 采用漏斗

把“看见—尝试—跑通—重复使用—生产依赖—贡献生态”分开。可以用以下观测量，但要注明口径：

- 尝试：安装/clone、首次成功启动；
- 激活：完成一个真实任务，而非只打开 Web；
- 重复使用：同一主体跨日/跨版本完成多个任务；
- 生产依赖：有负责人、SLO、升级/回滚、安全流程；
- 生态贡献：发布第三方插件、修复兼容、公开复现实验。

GitHub star 位于漏斗最上层，不能替代任何后续层。

## 冲突处理

官方说“支持”但用户报告失败时，不二选一：记录声明适用的版本与条件，复现用户路径，区分代码存在、默认挂载、已授权、平台实际强制和业务 E2E。结论写成“在 SHA X 的组合 Y 可复现/不可复现”，并保留反例。

## 首发快照的正确使用

发布首日的数据只建立时间锚点。之后的更新应以 diff 表述：版本与治理变化、第三方插件变化、主要争议变化、已关闭/新增风险，以及哪些学习文档因此过期。避免用累计 star 画“质量增长曲线”。
