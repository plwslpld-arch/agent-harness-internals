# Session、Context、Memory 与恢复：状态究竟保存在哪里

[上一篇：工具、权限与执行边界](03-tools-permissions-execution.md) · [返回学习入口](../00-start-here.md) · [下一篇：Trace、Eval 与结果核对](05-trace-eval.md)

![会话、上下文、记忆与压缩的关系](../../assets/diagrams/foundations/05-session-context-memory.svg)

Session、Context 和 Memory 经常被当作同义词，但阅读实现时必须把它们分开，它们不是同一层状态。Context 是某次模型请求实际能看见的输入，Session 记录一项任务怎样跨过多轮运行，Memory 保留的则是未来任务还可能用到的信息。Compaction 处理的是另一个问题：当历史过长时，它怎样把原始记录换成更短的表示。

## 用中断后的任务观察差异

假设运费修复已经读完文件并应用编辑，可进程在测试尚未运行时突然退出，那么系统重新启动后就需要回答：

- 用户原始目标是什么；
- 哪个文件已经修改；
- 编辑工具是否完成；
- 下一步应该运行什么测试；
- 之前的模型消息是否全部重新发送；
- 这次任务结束后，有哪些信息值得跨任务保存。

这些问题看上去都在问「之前发生了什么」，实际上却分别属于 Session、工具状态、Context 构造和 Memory 策略。

## Context：当前这一轮模型能看见什么

Context 通常由以下内容组合：

```text
稳定部分：系统指令、工具定义、项目规则
任务部分：用户目标、附件、初始环境信息
历史部分：模型消息、工具请求和工具结果
动态部分：工作目录、剩余预算、任务进展、权限模式
检索部分：按需加载的文件、记忆和外部知识
```

Context 并不等于数据库里的全部 Session，因为 Harness 还要结合模型窗口、缓存策略和当前任务阶段，选出这一轮真正需要发送的内容。

在运费案例里，恢复后的下一轮至少要让模型知道原始目标、已经应用的修改，以及那个尚未运行的测试。如果只把最近的「编辑成功」发给模型，它既可能不知道为什么编辑，也无法据此选出正确的测试。

## Session：任务的连续运行记录

Session 把多轮消息和执行事实关联到同一项任务，为了让这项任务能被追踪和恢复，一个实用的 Session 往往包含：

- 稳定标识；
- 创建和更新时间；
- 用户消息与模型消息；
- 工具调用、决定和结果；
- 当前运行配置；
- 取消、错误和结束原因；
- 压缩摘要及其覆盖范围；
- 外部产物引用。

Session Store 可以是文件、数据库、服务端存储，也可以是宿主应用提供的接口。无论存储形式怎样变，它都必须准确回答「哪些事件已经持久化」，以及「恢复应该从哪个提交点继续」。

聊天界面里显示的消息只是 Session 的一个投影，内部还可能保存不对用户展示的控制事件、Token 统计、审批记录和工具原始输出——界面不是完整记录。

## Runtime State：尚未成为消息的运行事实

有些状态不适合直接写入消息历史，例如：

- 当前正在执行的工具；
- 取消令牌；
- 流式响应已经接收的片段；
- 并行工具的完成集合；
- 尚未持久化的事件；
- 当前工作区句柄或进程 ID。

这类 Runtime State 可能只存在于内存，所以进程退出后，如果它们从未经过持久化接缝，恢复逻辑就只能把相关状态标成未知，不能假装已经完整重建——未知本身就是一种状态。

因此，源码文章要交代哪些状态可以恢复，以及哪些状态只能在当前进程中使用。看到一个 `resume(session_id)` API，不能据此推断所有正在执行的副作用都能无损恢复。

## Memory：跨任务保留的信息

Memory 服务的是未来任务，不是把所有 Session 原封不动地永久塞进模型输入，它通常会保留：

- 用户偏好；
- 项目约定；
- 已确认的环境事实；
- 经过整理的解决方案；
- 可复用 Skill 或指令；
- 外部知识索引。

运费修复中的某次具体工具调用，通常没有必要变成长期记忆。如果项目明确约定「金额单位使用整数分」或「提交前运行 shipping 测试」，那么这类稳定且可复用的规则更适合写入项目文档或 Memory。

Memory 写入不能没有来源和更新策略，因为一旦把未经验证的模型猜测直接跨会话保存，它就会在后续任务里一次次误导模型。

## Compaction：历史太长时保留什么

当消息历史接近模型窗口或成本预算，Harness 可以：

- 丢弃可重新获取的旧工具输出；
- 截断长日志并保留文件引用；
- 把早期消息总结成摘要；
- 保留最近若干轮原文；
- 固定关键任务状态和未完成步骤；
- 重新建立稳定前缀。

Compaction 要在缩短历史的同时，继续保留那些会影响后续决策的事实，如果只把旧消息简单删掉，任务就可能无法继续。摘要也会丢失信息。用户目标、已经产生的副作用、未完成步骤、约束和关键错误，都不能在摘要中消失。

在运费案例里，一份能支持继续工作的教学摘要可以这样写：

```text
目标：修复金额 100 时仍收费的问题。
已读取：src/shipping.ts。
已修改：条件 total > 100 改为 total >= 100。
尚未完成：运行 tests/shipping.test.ts 并确认边界断言。
```

如果摘要只写「已修复运费问题」，模型就可能跳过测试，在还没有证据时过早结束任务。

## 恢复流程的四个检查点

### 1. 加载 Session

先确认 Session 确实存在且版本兼容，然后找到最后一个完整持久化的事件。

### 2. 重建可恢复状态

恢复消息、配置、工作区引用和压缩摘要，而进程句柄等不可恢复对象，则要重新创建或者标记失效。

### 3. 处理未完成副作用

如果工具只留下开始事件，却没有结束事件，就要根据工具类型查询实际结果、请求用户判断，或者执行补偿。不能统一重跑。

### 4. 构造下一轮 Context

把原目标、已完成工作、未完成步骤和新环境状态交给模型，只要这些事实足以支持安全继续，恢复就无须回放全部历史。

## 消息重放与副作用重放不同

重新把旧消息发送给模型，通常不会改变外部世界，但重新执行旧工具却可能再次产生副作用。因此，Session 恢复必须区分：

| 对象 | 是否通常可以重建 | 主要风险 |
| --- | --- | --- |
| 用户和模型文本 | 可以 | 版本差异导致解释变化 |
| 工具结果消息 | 可以从存储恢复 | 原始输出可能已被截断 |
| 只读工具 | 可能重新执行 | 环境已经变化，结果不再相同 |
| 写入、支付、发送等工具 | 不能盲目重跑 | 重复副作用 |
| 进程内流式片段 | 常常不完整 | 无法知道 Provider 是否已结束 |

幂等键、外部操作 ID 和事务记录能够降低重复风险，但要让这些机制真正生效，每个工具都得先定义清楚自己的副作用语义。

## 在源码里怎么找

可以从公开入口开始，搜索 create、load、resume、fork、compact、history、store 等符号，然后回答：

1. Session ID 由谁生成；
2. 消息何时持久化；
3. 工具开始和结束是否分别记录；
4. Compaction 由长度、Token 还是显式请求触发；
5. 摘要怎样进入后续 Context；
6. 恢复是否重新连接 Provider 或执行环境；
7. 多客户端是否共享同一 Session 真值；
8. 哪些状态只存在于宿主内存。

如果只找到数据结构，却没有追到调用路径，仍然无法说明系统实际怎样恢复。还要继续查找负责创建、写入、读取和消费这些结构的函数。

## 回到运费案例

进程在编辑后退出，因此安全恢复时要先确认写入工具已有完成记录，加载修改后的工作区，再把「测试尚未运行」这个状态交给模型，让它继续验证。如果无法确认写入是否完成，就应当先读取文件或检查差异，而不是再次应用同一编辑。

任务结束后，可以把 Session 保存为审计记录，而长期 Memory 只应接收那些已经验证、未来仍然有用的项目规则。

## 现在应该能解释

Context 是一轮输入，Session 是一项任务的连续记录，Runtime State 保留当前进程的运行事实，Memory 服务未来任务，Compaction 则改写过长历史。恢复的核心在于安全重建继续任务所需的状态，同时避免重复产生副作用，把聊天重新演一遍并不能自动完成这些工作。
