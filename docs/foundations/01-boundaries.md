# Agent Harness 的职责与边界

## 读者会得到什么

读完本页，你应该能把一次 Agent 任务拆成四个可以分别记录的责任层：模型生成候选内容与工具意图，Agent Harness 装配上下文并控制行动循环，执行环境承载文件、进程和网络等真实资源，Eval 固定任务口径并解释运行产物。更重要的是，你会知道一个结果发生变化时，哪些证据足以支持归因，哪些比较因为同时改变了多层而只能标成「原因不明」。

这不是一套要求所有项目采用相同类名的架构标准。DSH、Codex、Gemini CLI、Claude 的公开 SDK、pi 与 OpenCode 会用不同模块切分责任，有些实现还会把多个阶段放进同一进程。本页给出的是阅读源码与设计实验时的分析坐标：先问「谁决定了这个行为」，再去锁定具体项目的文件、配置、测试和运行产物。

先锁边界，再谈比较。

## 核心概念

![一次 Agent 任务的四层职责与归因边界图](../../assets/diagrams/foundations/01-boundaries.svg)

Claim: foundation.boundaries.four-layers

### 四层不是四个进程

「层」表示责任边界，不表示部署拓扑。一个本地 CLI 可以同时包含 Harness 控制器、工具运行器和会话存储；一个服务化系统也可能把同一责任拆进多个进程。判断边界时应看输入、决策和输出，而不是看目录名、进程数或产品界面。例如，一个函数既发送模型请求又接收工具调用，并不意味着模型本身执行了工具；关键在于谁验证参数、谁批准副作用、谁把结果写回下一次请求。

| 责任层 | 主要输入 | 主要决策 | 主要输出 | 不应被默认归入 |
| --- | --- | --- | --- | --- |
| 模型 | 当前请求上下文、工具描述、采样配置 | 生成文本、推理内容或工具意图 | 内容块、工具调用、停止信号 | 文件写入是否成功、用户是否批准、评分器是否判通过 |
| Agent Harness | 用户目标、会话状态、模型输出、策略与工具注册表 | 上下文如何装配、暴露哪些工具、调用是否继续、何时恢复或终止 | 下一次模型请求、工具调度、会话事件、最终产物 | 模型参数内部机制、操作系统真正提供的隔离强度 |
| 执行环境 | 已批准的工具调用、工作目录、镜像、凭据与网络条件 | 资源是否存在、进程能否启动、系统调用是否被允许 | 标准输出、错误、文件变化、网络响应、退出状态 | 任务是否统计通过、失败是否允许重试 |
| Eval | 任务集、环境规范、Trial 标识、Trace、Artifact 与评分规则 | 什么算同一次试次、哪些失败可恢复、怎样评分与聚合 | 分数、失败分类、反馈、发布门槛证据 | 替 Agent Harness 决定下一次工具调用 |

模型层回答「提出什么候选行动」。它受到模型版本、权重、服务端行为、系统提示、可见历史和工具 Schema 的共同影响。只替换模型而保留其他配置，可以研究在该输入契约下的模型差异；但若新模型要求另一套工具格式、上下文长度或系统提示，比较已经不再是纯粹的模型替换，必须把适配变化一并记录。

Agent Harness 层回答「候选行动如何成为受控任务」。这里通常包含上下文装配、Provider 适配、工具注册与参数校验、权限策略、用户审批、Agent Loop、会话事件、压缩、恢复、终止和产物整理。某个项目可能把其中一部分交给扩展或服务端，因此「属于 Harness 的研究问题」不等于「必须在一个核心包内实现」。仓库后续六条主线会分别标注默认、可选、扩展、外部、缺失或未知，避免用统一框图抹掉差异。

执行环境层回答「动作实际上碰到了什么」。工作区内容、操作系统、容器镜像、安装依赖、网络、时钟、区域、凭据和资源配额都属于环境条件。Sandbox 是环境约束的一种实现，不是环境的同义词；用户看到权限确认，也不代表系统调用一定受到隔离。反过来，一个强隔离容器允许执行某条命令，也不能替代 Harness 的业务授权。

Eval 层回答「这次运行怎样被解释」。它需要固定任务与环境版本，确定统计单位，收集 Trace 和 Artifact，把结果交给 Scorer，再形成可比较的指标或反馈。Eval 可以启动 Agent Harness，也可以监听它的事件，但它不因此成为第二套 Agent Loop。Harness 能输出漂亮的轨迹同样不代表评测有效：如果任务泄漏、分母漂移或失败被不当重试，轨迹再完整也不能修复统计结论。

### 直接事实与分析框架

本页的关键 Claim 是 D 级推断，不伪装成某个上游已经声明的通用事实。锁定版本中，DSH 的 `docs/agent-lifecycle.zh.md:8` 明确把 `session/event` 的持久回放事实与 `agent/*` 的实时控制状态分开；Codex 的 `codex-rs/core/src/session/turn.rs:139-153` 明确描述 Turn 循环如何处理模型消息、执行函数调用并把结果送回下一次采样；Inspect AI 的 `src/inspect_ai/_eval/task/task.py:76-95` 则把数据集、Solver、Scorer 与 Sandbox 作为 Eval Task 的独立配置面。这些是三个项目的直接事实。

从这些事实可以推断，模型生成、任务编排、资源执行和结果评测至少能够作为不同观察面被记录。然而，「四层」名称、表格边界与单变量归因规则是本仓库采用的方法，不是 DSH、Codex 或 Inspect AI 联合发布的标准。读者若在某个项目中看到不同切分，应保留项目原语义，再把它映射到本页问题，而不是反过来修改源码含义以迁就框图。

### 谁应为失败负责

责任归类的目标是缩短验证链，不是把错误推给某一方。模型输出了不存在的文件名，首先记录为模型候选内容错误；Harness 把未通过参数校验的调用直接执行，首先记录为编排或策略错误；容器里缺少任务声明的编译器，首先记录为环境错误；正确产物被错误正则判成失败，首先记录为 Scorer 错误。一个失败可能有多层诱因，但每一条因果边都应有对应事件、配置或产物，不能凭最终分数猜测。

同样，成功也不能越层归功。模型建议了正确补丁，但 Harness 丢失工具结果后由人工补写，不能把最终成功全部记为模型能力；Harness 成功恢复了网络超时，只能说明恢复机制工作，不能把第一次基础设施失败抹掉；Eval 给出高分，只能支持在锁定任务、环境与评分规则下的结果，不能自动证明生产可用或安全。

## 为什么这样设计

四层拆分首先服务于可控变化。若模型请求、Harness 策略、执行镜像和评分器被装进一个无法拆解的「Agent 配置」，任何结果变化都会同时拥有多个解释。把每层输入、决定和输出单独记录后，实验才能明确哪些变量固定、哪一项被替换，以及观察到的差异最多能归到哪里。这种设计不要求组件物理分离，只要求证据能够沿责任边界分离。

第二个理由是让安全判断拥有两把不同的尺。Harness 的权限决定回答「这个主体在当前任务里是否获准做」，执行环境回答「即使获准，系统最多允许它碰到什么」。如果两者合并为一个布尔值，审批通过很容易被误读为隔离充分，容器允许也容易被误读为业务授权。保留策略决定与环境结果，才能区分越权请求、隔离缺口和普通执行失败。

第三个理由是让 Eval 保持独立。Harness 可以提供 Trace、Artifact 和运行状态，但不能自行改变 Trial 分母、把产品失败重试掉，或因为自己认为任务完成就宣告通过。评分器读取不可变产物并保留版本，既能发现 Harness 的实现缺陷，也能发现评分规则本身的错误。这里的独立强调结论不能由被评对象单方面改写，并不强求完全隔离部署。

最后，统一分析坐标只统一问题，不统一答案。六条主线都要回答模型请求在哪里形成、行动在哪里获批、资源在哪里受限、结果在哪里评分；但每个项目的模块、默认值和缺失能力仍按锁定证据书写。这样既能横向迁移方法，又不会把本仓库框图冒充上游规范。

## 最小例子

假设任务是「读取 `config.json`，把 `timeout` 从 30 改成 60，并保持其他字段不变」。基线运行锁定模型版本 `M1`、Harness 配置 `H1`、环境镜像 `E1` 和评分器 `S1`。模型先请求读取文件，Harness 校验路径并执行只读工具；模型随后发出编辑调用，Harness 根据策略请求批准，环境完成写入；Eval 比较最终 JSON 的字段和值，并保存调用轨迹与文件差异。

最小运行清单可以写成下面这样。这份仓库级记录用于归因，不对应某个 Provider 的请求格式：

```json
{
  "task": "config-timeout-001",
  "model": { "id": "M1", "sampling": "fixed" },
  "harness": { "id": "H1", "toolPolicy": "approve-write" },
  "environment": { "id": "E1", "fixture": "config-v1" },
  "eval": { "id": "S1", "trial": "T-001", "attempt": 1 }
}
```

如果只把 `M1` 换成 `M2`，而请求适配、工具 Schema、提示、环境和评分器保持可比，结果差异可以被限定为「模型替换在这套 Harness 契约下造成的差异」。它仍不是模型的普遍排名，因为任务样本只有一个，且外部服务可能存在未锁定因素。

如果只把 `H1` 的写入策略改成「禁止写入」，模型仍发出同样的编辑调用，最终任务失败。这个差异应归因于 Harness 策略，而不是说模型突然失去编辑能力。若 UI 没有弹出确认，也不能单凭界面断言没有策略；需要查看策略决策事件和实际工具分派记录。

如果只把环境 fixture 换成缺少 `config.json` 的 `E2`，读取工具返回文件不存在。此时失败发生在环境前置条件，不能用反复重新采样模型把它「重试成通过」。正确处理是把 Trial 保留在分母中，标注任务环境无效或基础设施失败，并按照预先定义的恢复规则决定是否新建 Attempt。

如果只把评分器 `S1` 换成错误地要求 `timeout` 为字符串的 `S2`，完全相同的文件产物会得到不同分数。这个变化属于 Eval 层；不能回头改写 Trace，声称 Harness 产生了不同结果。评分器版本、输入 Artifact 和评分输出必须一起保存，才能复核错误来自哪一步。

最危险的比较是四项一起换：新模型、新 Harness、新镜像和新评分器得到更高总分。这个结果可以作为新系统的整体观测，却不能回答提升来自哪里。若要形成因果解释，至少需要逐层消融，或明确声明结论只是端到端关联而不是单层归因。

### 一组失败反例

「模型 A 比模型 B 更会用工具」，但 A 使用带示例的工具说明，B 使用自动生成且丢字段的 Schema；这是模型层与 Harness 适配层同时变化。「Harness X 更安全」，但 X 在无网络容器运行，Y 在宿主机运行；这是策略与环境隔离混杂。「Agent 通过率更高」，但新版本把失败任务重新抽样到成功才计数；这是 Agent 行为与 Eval 分母混杂。三种说法都可能方向正确，却没有足够证据支持当前归因。

另一个常见反例是把产品表面当责任边界。CLI、IDE、Web 和 SDK 只是交互表面；它们可能共享同一 Harness 核心，也可能各自维护策略与会话。只有跟踪输入如何进入控制器、工具怎样分派、事件写到哪里，才能判断行为是否共享。后续项目文章会分别给出调用链，不使用「都有一个聊天框」作为同构证据。

## 最小实现

下面的最小实现不是完整 Harness，而是一个用于保存责任与因果的记录器。它先把每次任务绑定到四层版本，再要求所有事件声明责任层、输入引用、决定和产物引用。实现时按以下顺序推进：

1. 定义不可变的运行清单，包含任务、模型、Harness、环境、Eval 与各自版本；清单生成后只允许追加引用，不允许原地改写。
2. 定义统一事件信封，用 `run_id` 串起任务，用 `parent_event_id` 表达因果边，用 `layer` 标记当前决定的责任层。
3. 为工具请求、策略决定、执行结果和评分结果分别建立事件；拒绝必须声明 `executed: false`，执行失败必须保留环境状态。
4. 在结束时从 Score 反向遍历到 Artifact、Trace、Attempt、Trial 和运行清单；任一引用缺失都把结论标为不可判定，而不是默认通过。

```ts
type Layer = 'model' | 'harness' | 'environment' | 'eval';

type EvidenceEvent = {
  id: string;
  runId: string;
  parentEventId?: string;
  layer: Layer;
  kind: string;
  decision?: 'allow' | 'deny' | 'execute' | 'score';
  inputRefs: string[];
  artifactRefs: string[];
};
```

这个接口刻意没有把 `approved` 和 `succeeded` 合并。策略允许后，环境仍可能失败；环境产生文件后，评分器仍可能判失败；评分器判通过后，结论仍只覆盖锁定任务。最小实现的价值在于迫使每个状态拥有明确所有者，而不是提供一套可直接投入生产的事件平台。

## 常见误区

第一，Harness 不是模型的包装壳。它不仅负责发一个 API 请求，还可能改变模型看到的历史、工具、策略提示与恢复上下文，并控制真实副作用。忽略这些机制，会把系统工程差异错误记到模型能力上。

第二，环境不是 Sandbox 的同义词。环境包含所有外部状态，Sandbox 只描述其中一类隔离机制。是否展示审批、是否允许工具、是否能访问网络、操作系统最终是否阻断调用，是四个需要分别核对的问题。

第三，Eval 不是与 Agent Harness 并列的第二套百科，也不是「跑几个例子看看」。它是贯穿每条 Harness 主线的验证能力：同一条工具调用如何留下 Trace、同一产物如何进入 Scorer、同一次 Trial 如何处理基础设施恢复，都必须回到具体实现和统计契约。

第四，文件名不是行为证明。看到 `session`、`policy`、`sandbox` 或 `evals` 目录，只能把它列为候选证据。正式结论仍需锁定 Commit、具体行号、上游测试或实验产物，并说明平台与模式。若源码只证明「有这个类型」，就不能升级成「默认启用且可靠」。

第五，总分不能自动给出归因。端到端分数适合回答「这套锁定系统在这套任务上表现怎样」，不直接回答「哪个组件导致差异」。组件结论需要控制变量、足够样本和可复核运行记录；缺少任一项就应降低证据等级。

## 验证方法

第一步是为每次运行生成不可混淆的清单：任务与数据版本、模型和采样配置、Harness Commit 与功能开关、工具注册表与策略、环境镜像与 fixture、网络和凭据条件、Eval 版本、Trial/Attempt 标识以及 Scorer 配置。配置只保存在终端输出里不够，因为后续无法判断重跑使用了什么。

第二步是建立逐层可观察性。模型层至少保留经过脱敏的实际请求结构和响应事件；Harness 层保留上下文装配、策略决策、工具调用关联、终止与恢复事件；环境层保留退出码、文件差异和受控资源日志；Eval 层保留 Trial、Attempt、Trace、Artifact、Score 与失败分类之间的引用。敏感字段可以哈希或删除，但删除规则也要版本化。

第三步是做单变量反例。只换模型时确认工具 Schema 与上下文没有漂移；只换 Harness 时确认模型、环境和评分器一致；只换环境时确认任务 fixture 与资源差异是预期变量；只换 Scorer 时对同一份不可变 Artifact 重新评分。任何无法固定的因素都应进入限制说明，而不是默认为相同。

第四步是检查终止后的证据链。最终回复、补丁或文件只是 Artifact；还要能够回到生成它的 Trace、对应 Trial 和 Attempt，再回到锁定配置。若某个产品失败被新的 Attempt 覆盖成成功，或者评分器读取了与 Trace 不对应的文件，评测链已经断裂。

本页自身的验证边界也必须清楚：三个上游证据面支持职责可以分别观察，不直接证明所有 Harness 都完整实现四层，更不证明四层之间永远没有交叉。因此关键 Claim 保持 D 级；后续每条项目主线会把能直接核验的行为降落到该项目自己的 B、C、D 或 U 级结论。

## 验证练习

用同一个「修改 JSON 单字段」任务做四轮运行。第一轮固定全部配置作为基线；第二轮只让 Harness 拒绝写入；第三轮恢复 Harness 策略，但让环境以只读挂载阻断写入；第四轮复用第三轮 Artifact，却故意让评分器读取错误字段类型。每轮都保留相同任务标识和不同运行标识，并填写四层版本表。

验收时不要只看最终通过率。第二轮应出现策略拒绝且没有执行开始事件，第三轮应出现策略允许、执行开始和环境失败，第四轮应证明文件产物没有变化但 Score 改变。若日志把第二、三轮都压成「工具失败」，说明责任模型不足；若第四轮生成了新的 Agent Trace，说明评测没有真正复用不可变 Artifact。

最后交换同伴复核：让复核者只看事件与引用，不看你的结论，独立写出每轮失败属于哪一层以及证据覆盖范围。两人的归因不一致时，先补事件或限定条件，不用投票决定。练习产物应包含四份运行清单、事件序列、Artifact 哈希、四份 Score 和一页差异说明，它们共同构成可复核证据，而不是一次演示截图。

## 自检

### 问题 1

模型返回了正确工具调用，但文件没有变化，能否直接判定模型失败？

**答案：** 不能。应先核对 Harness 是否接收并校验了调用、策略是否允许或要求审批、工具是否被实际分派，以及环境是否成功执行。模型候选行动正确只覆盖模型层；最终副作用还跨越 Harness 与环境层。

### 问题 2

两个系统使用同一模型，为什么仍不能把分数差异直接归因于 Harness？

**答案：** 同一模型标识并不保证请求上下文、工具 Schema、采样配置、环境、任务集和评分器相同。只有这些因素保持可比，且运行链可复核，差异才可以被限定为 Harness 相关；否则只能描述端到端系统差异。

### 问题 3

权限弹窗通过后，是否说明命令已经在安全 Sandbox 中运行？

**答案：** 不是。弹窗属于策略或用户审批表面，Sandbox 属于环境隔离表面。需要另外核对实际执行后端、平台支持、挂载与网络限制，以及隔离失败时的回退行为。

### 问题 4

为什么本页的四层 Claim 是 D 级而不是 C 级？

**答案：** 上游源码和文档直接证明各项目存在可区分的控制、循环、任务与评分表面，但没有任何一个来源直接声明本仓库这套四层命名和单变量归因规则。后者是综合多个证据面形成的明确分析推断，所以必须保留 D 级和推断说明。
