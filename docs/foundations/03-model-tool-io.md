# 模型消息、工具调用与工具结果

## 读者会得到什么

本页解释一条工具调用怎样跨过三种表示：Agent Harness 自己的会话消息、模型服务的请求与响应格式、工具执行器的输入与输出。读完后，你应该能检查角色、内容块、调用标识、参数、错误和顺序是否在转换中保持语义，而不会把某一家 Provider 的 JSON 当成所有 Harness 都应使用的协议。

你也会看到两个刻意不同的锁定实现。Claude Agent SDK Python 的公开类型用 `ToolUseBlock.id` 与 `ToolResultBlock.tool_use_id` 关联调用和结果；OpenCode 的内部转换用同一个 `tool.id` 构造调用与结果，并按执行位置决定结果进入助手内容还是 `tool` 角色消息。共同点是关联不能丢，差异则必须保留。

字段可以改名。语义不能走失。

先保住语义。再转换格式。错误也要关联。顺序必须可解释。

消息必须闭合。调用必须唯一。结果必须对应。错误必须保真。

关联不可猜测。适配不可静默。

## 核心概念

![模型消息、工具调用和工具结果经过适配与执行的数据流图](../../assets/diagrams/foundations/03-model-tool-io.svg)

### 三种表示各自负责什么

第一种是 Harness 内部规范消息。这里的「规范」只表示该项目选择的稳定内部语义，不表示行业标准。它要能持久保存指令、用户输入、助手内容、工具调用、工具结果、错误与必要元数据，并支持会话恢复、Provider 切换和上下文重建。内部格式若直接等同某个模型服务的原始 JSON，日后切换服务时，持久历史会被旧 Provider 的角色和字段绑死。

第二种是 Provider 适配格式。适配器把内部指令映射到服务支持的 system、developer、user 或其他层级，把工具定义转换为该服务的 Schema，把内部消息序列化成请求，再把流式响应还原成文本、推理、工具调用与完成事件。这个边界最容易产生「看起来像成功」的数据损坏：字段被静默删除、工具参数增量拼错、角色顺序不合法，或者旧模型的专用元数据被错误复用到新模型。

第三种是工具执行记录。执行器需要稳定调用标识、工具名称、完成参数、策略上下文和取消信号；返回时还要带回结果内容、错误状态、结构化详情、媒体引用与副作用证据。它不应直接接收半截流式参数，也不应把人类可读的一段错误文本当成唯一机器状态。

三种表示可以使用不同字段，却必须共享一条可追踪语义链。模型调用 `A17` 请求读取文件；执行器记录 `A17`；工具结果仍指向 `A17`；下一次模型请求里也能识别它是该调用的结果。若中途重新生成 ID，Trace 无法闭合；若只靠数组位置关联，并行工具完成顺序变化后就可能把结果配错。

### 角色不是现实身份

消息角色是协议结构，不总是现实说话者。Claude Agent SDK Python 的公开测试把 `tool_result` 内容块放进 `type: "user"` 的消息中，并通过 `tool_use_id` 指向工具调用。这里的 `user` 不表示真人手工输入了文件内容，而是公开 SDK 所暴露的消息契约。

OpenCode 的转换层则会把未由 Provider 执行的已完成工具结果转成 `Message.tool`，同时保留助手消息里的工具调用。由 Provider 执行的托管工具可以把调用和结果一起留在助手内容中。两种布局都能表达调用与结果；因此比较 Harness 时，应先解释角色语义，再比较关联、顺序与模型可见性，不能用角色名判断「谁真正执行了工具」。

system、developer 与 user 指令层也不是固定集合。有的服务支持多层指令，有的 Harness 会预先合并，有的会用普通文本模拟运行上下文。仓库文章应记录转换前的内部来源、转换后的服务请求和冲突优先级。只展示最终 Prompt 字符串，会丢失哪些内容来自仓库规则、用户输入或运行时注入。

### 工具 Schema 只是候选行动契约

工具定义通常包含名称、说明和参数 Schema。它告诉模型可以提出什么结构，不证明参数已经可信，更不授权执行。响应中的工具参数可能是流式增量，需要先按调用标识合并；完成后还要做 JSON 解析、Schema 校验、项目级语义检查与权限判断。字符串路径通过类型校验，不代表它在允许工作区内。

一次响应可以包含多个工具调用。每个调用都必须有独立标识；名称相同也不能合并。并行执行时，完成顺序可能不同于模型给出的顺序，Harness 要分别说明事件顺序、持久化顺序和下一次模型请求中的顺序。数组下标只在序列完全不可变时才勉强可用，不能替代稳定 ID。

工具结果至少要区分成功与错误。结果内容可以是文本、结构化对象、文件或图像引用；错误也可能包含可恢复说明、退出码和部分输出。把所有内容强制转成一个字符串，可能让模型还能读，却会破坏 Scorer、UI、恢复和审计需要的机器字段。

### 流式事件与最终消息

模型流常把文本、推理和工具参数拆成多个 delta。Harness 可以实时显示这些增量，但在持久化最终工具调用前必须处理重复片段、乱序保护、取消和不完整 JSON。流结束事件不必等同工具参数有效；长度截断时，即使片段能被宽松解析，也不应默认执行。

最终消息是对流式事件的归并结果，不应反过来抹掉原始 Trace。调试「UI 显示正确但模型下一轮看错」时，需要同时检查原始 Provider 事件、内部归并消息和下一次序列化请求。只保留最后一份 JSON，无法判断错误发生在模型、解析器还是上下文构造器。

Provider 元数据也需要作用域。OpenCode 的锁定转换在 `to-llm-message.ts:70-94` 先判断历史消息与当前模型是否相同且没有消息错误，再决定是否复用 Provider 元数据。这个实现事实不能扩大成所有 Provider 的缓存规则，却很好地说明：签名、延续令牌或托管工具元数据可能只对原模型有效，跨模型恢复时必须有显式处理。

## 最小例子

下面是一组仓库级说明格式，用来展示语义，不是 Claude、OpenAI、Gemini 或其他服务的实际 API。它把指令来源、对话内容和工具定义分开，便于读者观察适配器需要转换什么：

```json
{
  "instructions": [
    {"scope": "repository", "content": "只读取工作区内文件"},
    {"scope": "user", "content": "读取 README.md 的标题"}
  ],
  "conversation": [],
  "tools": [
    {"name": "read_file", "schema": {"type": "object", "required": ["path"]}}
  ]
}
```

模型响应被内部适配为一个工具调用。`call_id` 是关联主键；`args` 在这里已经完成流式归并，但尚未代表策略允许：

```json
{
  "type": "tool_call",
  "call_id": "A17",
  "name": "read_file",
  "args": {"path": "README.md"}
}
```

执行器完成校验和读取后，返回同一个调用标识。结果既保留机器状态，也给模型可读内容：

```json
{
  "type": "tool_result",
  "call_id": "A17",
  "status": "ok",
  "content": [{"type": "text", "text": "# Agent Harness 内部原理"}],
  "details": {"bytes": 31}
}
```

如果文件不存在，不能把结果伪装成一条普通成功文本。最小错误仍应保留 `A17`、错误状态和稳定分类，例如 `not_found`；人类可读说明可以放在 `content`，平台错误放在 `details`。下一次模型请求因此知道哪一个调用失败，也能选择修正路径，而 Eval 可以把错误与环境前置条件对应起来。

这个例子在 Claude Agent SDK Python 的公开类型里可能映射成 `ToolUseBlock(id="A17")` 与 `ToolResultBlock(tool_use_id="A17")`；在 OpenCode 的转换层里，调用与结果都由相同的内部 `tool.id` 生成。映射只说明关联方式相似，不说明两者角色、序列化、托管工具或错误结构相同。

### 锁定证据怎样支持结论

Claude Agent SDK Python 的 `src/claude_agent_sdk/types.py:949-964` 直接定义 `ToolUseBlock.id`、`name`、`input`，以及 `ToolResultBlock.tool_use_id`、`content`、`is_error`。上游 `tests/test_message_parser.py:113-155` 验证结果块保留 `tool_789`，错误结果也保留 `tool_error` 和 `is_error`。这些是公开 SDK 契约证据，不是闭源 Claude Code 内部执行器证据。

OpenCode 的 `packages/core/src/session/runner/to-llm-message.ts:30-66` 用同一个 `tool.id` 构造 `ToolCallPart` 与成功或错误的 `ToolResultPart`；`88-112` 决定 Provider 执行结果与本地执行结果怎样进入模型消息。上游测试 `session-runner-message.test.ts:235-287` 同时断言助手工具调用和 `tool` 角色结果，并保持 `completed` 等 ID 一致。

这四个证据面足以支持「稳定关联在两种实现中都可直接观察」。但「工具结果必须关联并重新进入后续模型上下文」是本仓库对完整 Agent Loop 的共同要求，字段与角色映射由项目决定，所以 Claim 使用 D 级。若某个 Harness 选择用不可变复合键而不是字符串 ID，也应先验证等价语义，而不是因字段名不同判定缺失。

## 常见误区

第一，把 Provider 原始 JSON 直接叫作 Harness 的通用消息。它可能包含服务专用角色、签名、缓存或托管工具字段；长期持久化前需要明确兼容策略。能成功发出一次请求，不等于能跨版本恢复。

第二，看到 `user` 角色就认定内容来自真人。工具结果、运行上下文或协议兼容层都可能使用这个角色。现实来源应放在独立元数据或事件类型里，不能只靠角色猜。

第三，只校验工具参数能否解析。合法 JSON 仍可能缺字段、越界、指向工作区外或违反业务策略。解析、Schema、语义、授权和隔离是连续但不同的检查。

第四，用工具数组位置关联结果。并行、重试、Provider 托管工具和消息压缩都会改变序列。稳定调用标识必须随调用、执行、结果和下一次模型输入贯通。

第五，把错误压成普通文本。这样会丢失错误分类、是否执行过、副作用范围和可恢复性。模型可能继续回复，但 Trace 与 Eval 无法区分产品失败、策略拒绝和基础设施故障。

## 验证方法

先建立黄金往返测试：内部消息序列化成 Provider 请求，再用录制响应解析回内部消息。断言指令来源、角色顺序、内容块类型、工具名称、参数和调用标识没有丢失；不要只做快照目视比较，还要有字段级不变量。

再覆盖工具结果。为成功、错误、空内容、结构化内容、媒体、Provider 托管执行和本地执行分别构造调用与结果，确认结果只能关联到一个已存在调用，未知或重复 ID 会显式失败。并行调用要故意交换完成顺序，检查关联不受数组位置影响。

然后覆盖流式边界。把一个工具参数拆成多段，注入重复 delta、取消和长度截断；断言参数完成前不执行，取消后不产生静默副作用，不完整调用被记录为错误或未完成状态。流式 UI 正确只是附加检查，最终还要核对下一次模型请求。

接着测试 Provider 切换与恢复。用模型 A 产生含专用元数据的历史，再由模型 B 构造请求，确认不兼容签名不会盲目复用，调用与结果的可读语义仍然存在。若项目不支持跨 Provider 恢复，应明确拒绝并给出可诊断错误，而不是生成一份看似合法的坏请求。

最后把证据串起来：原始响应事件能回到内部工具调用，执行记录能回到同一调用，工具结果能出现在下一次模型可见请求，最终回复能引用结果。缺一环，就不能声称工具闭环完成。

禁止跳过中间层。结果必须能回送。错误必须可定位。

## 自检

### 问题 1

为什么工具调用和结果不能只靠数组位置配对？

**答案：** 并行完成、重试、托管工具和上下文重建都可能改变顺序。稳定调用标识能跨响应、执行、持久化和下一次请求保持关联，数组位置不能提供同样保证。

### 问题 2

Claude Agent SDK 的工具结果出现在 `user` 消息中，是否说明结果来自真人？

**答案：** 不能。`user` 是该公开 SDK 契约中的消息角色，工具结果仍通过 `tool_use_id` 表明真实语义。现实来源必须由内容块类型和事件元数据判断。

### 问题 3

工具参数已经是合法 JSON，为什么仍不能执行？

**答案：** 合法 JSON 只通过语法层。还需要 Schema、业务语义、路径边界、权限策略、用户审批与执行环境约束；任何一层都可能拒绝。

### 问题 4

为什么关键 Claim 是 D 级，而不是把两套源码合并成 C 级通则？

**答案：** 每套源码只直接证明本项目的公开类型或转换行为。稳定关联的共同需求是跨两个实现形成的分析推断，角色、字段与 Provider 元数据处理仍不同，所以必须保留 D 级和适用边界。
