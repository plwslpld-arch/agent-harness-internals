# 一次任务怎样形成 Agent Loop

[上一篇：Model、Harness 与 Environment](01-model-harness-environment.md) · [返回学习入口](../00-start-here.md) · [下一篇：工具、权限与执行边界](03-tools-permissions-execution.md)

![一次 Agent 轮次和完整任务的关系](../assets/diagrams/foundations/02-agent-turn.svg)

Agent Loop 并不只是「反复调用模型」，因为每一轮都要确定输入、消费模型输出、处理工具或文本分支、保存新状态，然后依据可观察条件决定下一步——一旦某个环节含糊，任务就可能无限循环、过早结束，或者在恢复后重复副作用。

## 一轮和一个任务不是同一个单位

在运费案例里，完成任务需要多轮：

1. 用户提出修复目标；
2. 模型请求读取实现；
3. 文件结果返回后，模型请求编辑；
4. 编辑结果返回后，模型请求运行测试；
5. 测试结果返回后，模型给出最终答复。

一次模型请求和响应可以称为一轮，而一个任务通常由多轮组成，其中还包含轮次之间的工具执行、状态保存和错误处理。

不同项目会使用 Turn、Step、Cycle、Iteration、Run、Task、Thread 等术语，但文章不会假设这些词天然等价，而是会在每条课程开头给出项目自己的层级关系。

## 第一轮：构造模型真正看见的输入

用户消息只有一句，但模型输入通常还包括系统指令、工具定义、会话历史和运行状态：

```json
{
  "system": "你在受控工作区中修改代码。修改后运行相关测试。",
  "tools": ["read_file", "edit_file", "run_command"],
  "messages": [
    {
      "role": "user",
      "content": "修复订单金额为 100 元时仍收取运费的问题，并运行测试。"
    }
  ],
  "runtime": {
    "workspace": "当前仓库",
    "approval_mode": "按风险询问"
  }
}
```

这些只是教学数据，不对应某个厂商 API，因为真实项目可能把 system、tools 和 runtime 分成不同请求字段，也可能把动态状态注入系统提示。读源码时，要追踪最终发送给 Provider 的对象，不能只看配置文件里的原始值。

## 第二步：消费模型输出

模型输出可能有多种形态：

- 普通文本；
- 一个工具调用；
- 多个可并行工具调用；
- 流式文本和工具参数片段；
- 明确结束原因；
- 被取消、不完整或解析失败的响应。

Harness 必须把这些形态转换成内部事件或状态，而当工具参数以流式 JSON 片段到达时，只有等它们拼接并解析成功，才能进入工具层。如果响应在参数完成前就中断，系统不能把半截参数当作有效命令。

在运费案例中，第一轮理想输出是读取文件，而不是直接修改：

```json
{
  "id": "call-read-1",
  "name": "read_file",
  "arguments": {"path": "src/shipping.ts"}
}
```

调用 ID 必须稳定——只有这样，它才能把模型请求、权限决定、执行结果和下一轮消息可靠地关联在一起。

## 工具结果怎样进入下一轮

![模型请求工具与工具结果回填的时序](../assets/diagrams/foundations/03-model-tool-io.svg)

文件工具执行后，Harness 通常会生成一条与原调用关联的结果消息：

```json
{
  "tool_call_id": "call-read-1",
  "status": "success",
  "content": "export function shippingFee(total) { return total > 100 ? 0 : 10 }"
}
```

下一轮不会只发送工具结果，Harness 还会把系统指令、必要历史、工具定义和新结果重新组合。某些 Provider 支持缓存稳定前缀，而某些项目会在预算紧张时压缩旧历史，这些决定都会改变模型真正能用的信息。

编辑和测试也遵循同一种模式，先由模型提出请求，再由 Harness 控制执行，结果最后成为下一轮的新观察。

## 循环状态应该显式保存什么

一个可恢复的 Loop 至少需要知道：

| 状态 | 用途 |
| --- | --- |
| 任务或 Session 标识 | 把多轮事件归到同一任务 |
| 当前消息历史 | 构造下一次模型输入 |
| 工具调用 ID 和执行状态 | 防止结果错配或重复副作用 |
| 取消与超时信号 | 让模型请求和工具执行可以停止 |
| Token 或轮次预算 | 防止无限循环 |
| 最后一个持久化位置 | 崩溃后判断从哪里恢复 |

如果只保存最终聊天文本，恢复时就无法知道某个写文件动作是否已经发生，因此系统可能重新执行同一工具，也可能在丢掉工具结果后让模型再次提出相同请求。

## 什么时候继续

以下情况通常需要继续循环：

- 模型提出了一个可以处理的工具请求；
- 工具执行结束，结果需要交给模型解释；
- 权限被拒绝，但拒绝原因作为新观察允许模型选择替代方案；
- 可恢复错误已经转化为结构化反馈。

继续循环并不等于重试原操作，因为权限被拒绝后，可以让模型改用只读工具，而命令失败后，也可以根据错误输出修正参数，下一轮要带着这些新信息。

## 什么时候结束

常见结束条件包括：

- 模型返回最终文本且没有待处理工具；
- 达到轮次、Token、时间或成本上限；
- 用户取消；
- 协议错误无法恢复；
- Environment 不再可用；
- 产品策略要求停下并交给用户。

「模型没有工具调用」只是一个信号，如果测试仍然失败，那么模型即使给出「已经修复」的文本，也不代表任务结果正确，因此 Harness 可以结束运行，但任务判定仍需要测试或 Eval。

## 一个最小状态机

下面用教学状态机把这些转换关系串起来。

```text
准备输入
  │
  ▼
请求模型 ──错误──> 记录失败 ──可恢复──> 准备输入
  │                              └─不可恢复──> 结束
  ▼
解析响应
  ├─最终文本──────────────> 保存输出 ──> 结束
  └─工具请求
       │
       ▼
    检查与执行
       │
       ▼
    写入工具结果 ─────────> 准备输入
```

真实实现可能使用异步生成器、事件总线、递归函数或显式 reducer，所以阅读时不必强迫它长得像这张图，形态并不关键，只要能找出状态和转换条件就够了。

## 过早结束的三个例子

### 编辑成功就结束

文件写入成功只能证明补丁已经落盘，但不能证明代码可以编译或测试能够通过，因此正确流程还应继续调用验证工具。

### 命令退出码为 0 就结束

即使运行了错误的测试文件，命令也可能返回 0，所以 Harness 还要让模型或验证器确认命令确实与任务目标对应。

### 模型说完成就结束

模型文本只是候选解释，因此对于可验证任务，结束条件应尽量包含环境事实，例如相关测试输出和预期文件差异。

## 无限循环从哪里来

典型循环包括：

- 模型反复读取同一文件，没有新的状态提示；
- 工具输出被截断，模型每轮都重新请求完整内容；
- 权限拒绝没有作为结果返回，模型不知道请求被拒；
- 失败命令只返回「失败」，缺少可以修正的错误信息；
- 历史压缩丢掉了已经完成的步骤。

解决这些问题时，只设置最大轮数并不够，Harness 还要把调用计数、拒绝原因、结构化错误、任务进展和压缩摘要放回可见状态中。

## 阅读真实 Loop 的顺序

进入源码后按以下顺序定位：

1. 找到公开入口怎样创建任务或 Session；
2. 找到发起模型请求的函数；
3. 找到响应类型和流式消费逻辑；
4. 找到工具请求分支；
5. 找到工具结果写回消息的位置；
6. 找到最终文本、限制、取消和错误的结束分支；
7. 找到状态持久化发生在转换前还是转换后。

等一条调用链完整跟完后，再去阅读并行工具、子代理、压缩和恢复，因为如果直接从扩展功能开始，很容易错过核心状态机。

## 回到运费案例

任务真正形成闭环，需要保留这样一条事实链：

```text
失败测试
→ 读取实现
→ 确认边界条件
→ 编辑比较符
→ 运行目标测试
→ 观察金额 100 的断言通过
→ 生成最终答复
```

如果缺少「目标测试」或「金额 100 的断言」，最终答复就会失去可核对的依据。Loop 负责把过程一步步向前推进，而任务判定负责解释最终结果，两者会在闭环的最后一步相遇。

## 现在应该能解释

一轮是一次模型交互，而一个任务由多轮交互和其间的工具执行共同组成。工具结果会成为下一轮的新观察，而结束条件既要处理协议和资源限制，也要避免把模型声明误当成环境事实。声明不是事实。
