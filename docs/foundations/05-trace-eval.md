# Trace、Eval 与结果核对：运行结束不等于任务正确

[上一篇：Session、Context、Memory 与恢复](04-session-context-memory.md) · [返回学习入口](../00-start-here.md)

![运行轨迹、环境产物与独立评测的关系](../assets/diagrams/foundations/06-trace-feedback-eval.svg)

Harness 可以顺利结束一项任务，最终结果却依然可能是错的。结束只说明循环停了——Trace 把运行过程变得可观察，而 Eval 借助明确的任务定义和判定方法来解释结果。它们共同连接 Agent 运行与质量判断，但没有必要挤进每一篇讲工具或 Session 的文章。

## 运费案例有三个不同结论

模型完成编辑并运行命令后，不能立刻用一个「成功」概括全部结果，至少要区分：

1. **运行是否正常结束**：模型请求、工具执行和消息循环有没有协议错误；
2. **目标测试是否通过**：测试进程是否运行了正确文件并返回预期断言；
3. **用户目标是否满足**：金额 100 的行为是否正确，同时没有破坏其他运费规则。

第一项描述 Harness 的运行健康，第二项记录环境中确实发生的事实，第三项则要回到任务口径作出判定。只看最终答复，无法可靠回答后两项。

## Trace 应该记录什么

下面用一份教学数据展示最小 Trace 的事件构成。

```json
{
  "task_id": "shipping-boundary",
  "events": [
    {"type": "user_message", "content": "修复金额 100 时仍收费的问题"},
    {"type": "tool_call", "id": "read-1", "tool": "read_file"},
    {"type": "tool_result", "id": "read-1", "status": "success"},
    {"type": "tool_call", "id": "edit-1", "tool": "edit_file"},
    {"type": "tool_result", "id": "edit-1", "status": "success"},
    {"type": "tool_call", "id": "test-1", "tool": "run_command"},
    {"type": "tool_result", "id": "test-1", "exit_code": 0},
    {"type": "final_message"}
  ]
}
```

上面是一份教学数据，真实项目里可能换成 JSONL、数据库事件、协议通知或内存对象。具体载体可以不同，关键是顺序和关联标识必须保留，否则读者就无法回答「什么请求导致了什么结果」。

Trace 不一定需要保存所有原始内容，敏感字段、超长日志和二进制产物都可以只保留引用或哈希。不过，消费者必须知道数据是否完整，以及它是否经过截断或脱敏。

## 最终文本为什么不够

模型可能说「测试已经全部通过」，但存在多种反例：

- 测试命令没有真正执行；
- 执行的是错误目录中的测试；
- 输出属于旧进程；
- 只跑了不覆盖金额 100 的测试；
- 测试通过，但修改了无关文件；
- 最终回复在测试失败后仍声称完成。

因为最终文本可以和实际执行完全脱节，所以对于可验证任务，评分器应该优先读取环境产物，不要只判断一段结论听起来是否可信。

## Eval 的最小组成

一个可解释的 Eval 至少需要：

| 组成 | 在案例中的内容 |
| --- | --- |
| Task | 修复金额 100 的免运费边界，并运行测试 |
| Initial Environment | 固定版本的仓库和依赖 |
| Runner | 使用目标 Harness 执行任务 |
| Trace 与 Artifact | 消息、工具事件、补丁、测试输出 |
| Evaluator | 检查目标断言、回归测试和文件差异 |
| Result | 通过、失败或无法判断，并附原因 |

这里的 Evaluator 可以是确定性测试、规则、人工审查，也可以由模型评分。只要环境里存在可直接判断的真值，就应优先使用确定性方法。

## 过程正确和结果正确

目标测试通过，不代表完成任务的过程一定可接受，因为 Agent 可能删掉失败测试、把结果硬编码进输出，或者改动大量无关文件。通过也可能是伪装。为了识别这些假成功，Eval 可以同时检查：

- **结果条件**：金额 100 返回 0，其他边界仍正确；
- **过程条件**：没有越界写文件，没有修改测试来迎合实现；
- **资源条件**：运行时间、模型调用和工具次数处于合理范围；
- **证据条件**：补丁和测试输出确实属于本次任务。

过程条件不应只写在提示词里，因为模型是否遵守过程要求，最终还得回到可观察证据上。凡是可以验证的规则，都应尽量落到文件差异、权限事件和测试中。

## 失败、无法运行和无法判断

评测结果至少要区分：

- **任务失败**：运行完成，但用户目标没有满足；
- **环境阻塞**：依赖、网络或执行环境无法启动任务；
- **结果不完整**：缺少必要产物，无法可靠判定；
- **Harness 错误**：协议、工具或持久化发生故障；
- **用户取消**：任务主动终止。

如果把所有情况都写成失败，产品质量统计就会被污染，可如果直接丢弃环境错误，运行健康问题又会被隐藏。后续的高级 Eval 专题会继续讨论统计单位和恢复尝试，基础导读先把这些语义分开。

## 重试为什么会改变解释

如果测试服务只是偶发超时，可以在同一任务定义下重新建立一次运行尝试。重试不是免费机会——如果 Agent 确实修改错了，就不应连续重试到偶然成功，因为前一种做法是在恢复基础设施，后一种做法却会改变我们实际观测到的产品质量。

学习源码时，可以先沿着一次重试追问：

- 谁决定重试；
- 重试的是模型请求、工具调用还是整项任务；
- 旧的失败是否保留；
- 最终结果引用哪一次产物；
- 有副作用动作是否会重复。

比起记住某个评测框架的类名，这些问题更能帮你读懂重试究竟改变了什么。

## 从 Trace 回到源码

Trace 字段只有在能追到产生它的代码时才可靠，因此阅读项目时要继续寻找：

1. 事件类型或消息类型的定义；
2. 模型请求开始和结束的发射点；
3. 工具调用、权限决定和执行结果的关联方式；
4. Session 持久化使用的序号或时间；
5. 最终输出和错误怎样暴露给 CLI、SDK 或服务端；
6. 是否存在 OpenTelemetry、日志、回放或测试适配器。

某个项目提供了 Telemetry，不代表它已经拥有完整的任务 Eval，而项目里有测试，也不代表这些测试覆盖了真实运行轨迹。文章应当根据每个项目的实际能力说明这些接缝，不能统一宣称所有 Harness 都内建独立评测。

## 一个可复核的最小判定

对运费案例来说，下面这组确定性检查就能给出一个最小判定：

```text
1. 从固定仓库版本创建工作区
2. 让 Harness 执行用户任务
3. 保存补丁和工具事件
4. 在干净测试进程中运行目标测试与回归测试
5. 确认测试文件没有被修改
6. 把结果关联到本次任务和补丁
```

即使模型最终回复为空，只要补丁和测试事实完整，仍然可以判断任务结果。反过来，回复写得再自信，只要目标断言失败，任务就没有通过。

## 如何使用后续内容

六条源码课程只会在对应项目确实提供事件、日志、Telemetry 或 Eval 接缝时讲解它们。DeepSeek Harness 的评测相关实现会放回它自己的调用链中，而 Codex、Gemini CLI、Claude、pi 和 OpenCode 则只陈述锁定来源真正能够支持的能力。

跨项目评测、Trial 与 Attempt、RewardAdapter、训练反馈和独立发布评估都属于进阶专题，阅读基础 Agent Loop 时暂时不需要掌握。

## 练习：最终回复与任务结果冲突时相信谁

## 现在应该能解释

Harness 结束描述的是运行状态，测试输出描述的是环境事实，Eval 则根据任务口径解释结果。Trace 负责连接请求、决定和产物，而重试只有分清基础设施恢复与真实产品失败，才不会扭曲最终判定。
