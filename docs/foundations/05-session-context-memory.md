# Session、Context、Compaction 与 Memory

## 读者会得到什么

本页把长任务中的状态拆成五类：Session 身份与持久记录、为单次模型请求派生的 Context、缩短模型可见历史的 Compaction、从会话之外检索材料的 Memory，以及用于故障恢复的提交记录或检查点。读完后，你应该不会再用一句「模型记住了」同时指代数据库、消息数组、摘要、向量检索和进程内缓存。

最重要的工程结论是：恢复会话不等于重放命令。Harness 可以重读已经发生的事件来重建状态，却不能因此再次执行已经完成的写文件、付款或远程发布。若系统没有调用标识、提交状态和去重语义，Session 能恢复对话也不能证明任务可以安全恢复。

记录可以长久。上下文总是有限。边界必须清楚。

## 核心概念

![持久会话、单次上下文、压缩、外部记忆与恢复检查的中文生命周期图](../../assets/diagrams/foundations/05-session-context-memory.svg)

Claim: foundation.state.session-is-not-context

### Session 保存的是什么

Session 首先是生命周期身份。它通常关联会话编号、创建时间、项目或工作目录、父子关系和元数据，并为用户消息、模型响应、工具调用、工具结果、分支、摘要或自定义记录提供有序归属。具体存储可以是内存、JSONL、SQLite 或外部服务；「有 Session」本身不代表进程退出后仍可恢复。

持久 Session 还需要记录顺序和提交边界。仅保存最终聊天文本，会丢失工具调用与结果关联、审批、失败原因和真实副作用。理想记录应能回答某个调用是否只被提出、已经开始、已经成功提交、明确失败，还是状态未知。不同项目采用事件、事实表或消息树，字段不能强行统一。

Session 也不是整个工作环境。文件系统、Git、远程工单和数据库都可能包含会话之外的真实状态。Session 里的「文件已修改」只是记录；恢复时仍应检查文件或提交是否存在，不能把历史文本当成环境真相。

### Context 为什么只属于一次请求

Context 是 Harness 在调用模型前构造的有限、有序输入。它可能包含系统或开发者指令、选中的会话消息、工具 Schema、运行时信息、压缩摘要和检索结果，还要经过 Provider 协议适配。模型窗口、顺序规则和内容块格式会约束最终请求。

同一 Session 的连续两次模型请求，Context 可以不同。第一次请求后新增了工具结果，第二次就必须纳入；模式切换会改变工具集合；压缩会把旧消息替换为摘要；分支会选择另一条路径；动态指令和环境信息也可能变化。因此 Context 是可重建的派生视图，不应成为唯一权威记录。

pi 的锁定源码直接展示这种转换。`packages/agent/src/harness/session/context.ts:90-99` 先从路径条目推导状态并构造 Context 条目，再投影为模型消息。`75-79` 遇到 compaction 条目时生成摘要消息并附上保留尾部。这证明的是 pi 的公开源码行为；它支持本仓库的共同抽象，却不能规定其他项目的字段名。

### Compaction 做了什么，又丢了什么

Compaction 在 Context 接近窗口限制时，把较旧内容转成更短表示，保留较新的尾部。它可以是截断、规则提取、模型摘要，或多者组合。压缩目标是让下一次请求可继续，不是让原始历史与摘要在信息上等价。

摘要天然有损。摘要不是原文。它可能遗漏精确路径、命令参数、否定条件、工具错误、用户原话和未完成状态，也可能把推断写成事实。即使增加第二次模型自检，也只能降低风险，不能证明零遗漏。安全恢复不能只靠摘要中一句「操作已经完成」，应回到结构化调用记录和真实环境核验。

Gemini CLI 的锁定实现给出一个具体例子。`chatCompressionService.ts:323-351` 分割截断后的历史，并按容量选择原始或截断内容给摘要模型；`431-440` 用最终摘要、确认消息和保留尾部组成 `newHistory`。测试 `266-292` 验证超过阈值后得到已验证摘要并调用两次生成。这里的「双轮自检」是项目事实，不是所有 Harness 的必备算法。

压缩还会改变缓存前缀。Provider 的提示缓存通常依赖前缀内容与顺序；把数百条旧消息替换成新摘要后，即使任务语义近似，字节或令牌前缀也已经变化。缓存命中率、费用和延迟可能突变。不能把「Session ID 没变」推导成「模型缓存仍连续」。

### Memory 为什么不是更大的 Session

本仓库把 Memory 限定为从当前会话记录之外读取、并在请求时选择性注入的材料，例如用户偏好、项目惯例、知识库片段或跨会话摘要。它可能由核心能力提供，也可能是 `optional`、`extension` 或 `external`；没有直接证据时应写 `unknown`，不能从一个 memory 文件名推断默认启用。

Memory 检索有三类不确定性。相关性不确定意味着召回结果可能漏掉关键资料或带入噪声；时效不确定意味着旧规则可能已失效；权限不确定意味着索引可见不代表当前任务有权读取。候选材料必须经过来源、时间、权限和冲突检查后才能进入 Context。

Memory 不能覆盖权威事件。若检索结果声称发布已完成，而 Session 提交账本和远端状态没有证据，Harness 应把它视为待核验线索。反过来，删除 Memory 索引也不应删除 Session 的审计记录。两者可以互相引用，但职责不同。

### 锁定实现中的会话证据

Claude 公共 Python SDK 的参考 `InMemorySessionStore` 在 `session_store.py:35-46` 明确以 `project_key/session_id` 复合键保存条目，并说明进程退出后数据丢失；`64-85` 实现追加和读取。上游测试 `129-135` 还确认 `load()` 返回副本。这些只能证明公共 SDK 存储契约与参考适配器，不能推断闭源 Claude Code 客户端内部如何落盘或压缩。

pi 的 SQLite 存储在 `sessions.ts:54-75` 插入和读取会话身份、创建时间、元数据、工作目录与父会话；其 Context 构造器则位于另一模块。持久身份表与模型消息投影分离，是 Session 和 Context 不等价的项目级证据。是否保留全部事件还要继续核对条目表、删除与压缩实现，不能只看 sessions 表。

三组实现共同支持 D 级 Claim：持久 Session 与单次 Context 是不同状态表面。联合结论仍是推断，因为它们对持久性、分支、摘要、恢复、外部 Memory 和删除语义没有统一协议。文章采用共同词汇是为了比较，不是宣称行业标准已经存在。

## 为什么这样设计

Session 作为权威历史、Context 作为派生视图，是为了同时满足审计与模型窗口限制。权威记录关心「真实发生了什么」和提交顺序，Context 关心「这一请求需要看到什么」；若二者共用一份可变消息数组，压缩会销毁审计证据，恢复时的环境补充又会被误写成历史事实。派生视图可以重建、裁剪和适配，权威历史则按保留政策维护引用与不可变边界。

Compaction 单独建模，是因为摘要的正确性与历史提交的正确性不是同一问题。摘要可以失败、过时或遗漏，最坏结果应该是当前请求上下文不完整，而不是把已经发生的工具副作用改写掉。把摘要标成派生 Artifact，并记录来源范围、生成器与时间，复核者才能知道一句话来自原始用户输入、工具结果还是模型归纳。

Memory 放在会话之外，是为了保留来源、权限和时效检查。长期偏好、项目规则与跨会话知识可能对当前任务有帮助，却不属于本次任务已经发生的事件。检索结果进入 Context 前要携带来源和更新时间；与当前 Session 或环境冲突时，权威事实优先。否则一条旧记忆就可能覆盖新规则，且使用者无法解释模型为何看到它。

恢复账本与会话浏览分开，是为了避免重放副作用。重读事件用于计算「目前知道什么」，真正再次执行则需要提交状态、幂等键和外部核验。若一次发布在远端成功但本地结果落盘前崩溃，聊天记录缺少成功消息并不等于可以再发布。恢复器必须把「未开始、已提交、明确失败、状态未知」作为不同状态处理。

## 最小例子

假设一个长会话先把 `report.json` 写入工作区，又准备把制品发布到远端。下面是本仓库建议的抽象事件格式，不是任何上游产品的实际 API：

```json
[
  {"seq": 41, "kind": "tool_call", "call_id": "W7", "tool": "write_file"},
  {"seq": 42, "kind": "tool_result", "call_id": "W7", "status": "committed", "artifact": "report.json"},
  {"seq": 43, "kind": "tool_call", "call_id": "P8", "tool": "publish", "dedupe_key": "release-2026-08-23"},
  {"seq": 44, "kind": "recovery_point", "last_committed_seq": 42}
]
```

当 Context 过长时，Harness 可以生成「报告已写入；远端发布尚未确认」的摘要，并保留最近事件。下一次模型请求只看到摘要、近期尾部和当前工具集合；权威 Session 仍应保留或可追溯到 `W7` 的提交证据。若某实现确实删除原始条目，则必须把这项差异写入能力和恢复限制，不能假装仍可审计。

进程在 `P8` 返回前崩溃后，恢复器先读取最后提交序号，再查询真实远端是否已有 `release-2026-08-23`。若远端已提交，就补记结果而不再次发布；若确定未开始，可以沿同一去重键重试；若状态无法判定，则进入人工或补偿流程。仅凭缺少 `tool_result` 就重放发布，可能制造重复副作用。

这个例子还说明 Attempt 与 Session 的区别。同一未决调用可以有恢复 Attempt，但产品副作用不能通过无约束重试变成多个成功。用于 Eval 的统计规则将在下一篇固定；这里先确立恢复不变量：历史回放只重建状态，真实命令是否再执行必须经过提交状态、幂等性和环境核验。

### 原始事件是否必须永远保留

审计敏感任务应优先保存不可变原始事件或可验证归档，并把摘要作为派生记录。成本、隐私和保留政策也可能要求裁剪或删除；此时必须明确哪些证据不可恢复、摘要由谁生成、何时失效，以及删除是否传播到缓存和 Memory。保留全部原文是推荐契约，不是本文对所有上游的事实断言。

## 最小实现

用一个追加式事件文件和一个纯 Context 构造器就能验证核心边界，不必先实现数据库或向量检索：

1. 为 Session 建立递增序号，只追加用户、模型、工具、提交与摘要事件；工具调用同时保存调用 ID、去重键和提交状态。
2. 实现 `buildContext(session, budget)`，从选定分支读取事件、插入有效摘要并保留尾部，返回本次请求消息和每条内容的来源引用。
3. 实现 Compaction，把指定序号范围生成摘要 Artifact；原事件仍保留，摘要不得修改工具提交状态。
4. 模拟崩溃后读取事件归约状态；只有确认未开始或外部幂等核验允许时才能创建恢复执行，状态未知则阻断。

```ts
type CommitState = 'requested' | 'started' | 'committed' | 'failed' | 'unknown';

type ContextItem = {
  content: string;
  source: { kind: 'session' | 'summary' | 'memory' | 'runtime'; ref: string };
};

function mayReplay(state: CommitState): boolean {
  return state === 'requested';
}
```

`mayReplay` 有意采用保守规则：`started` 不能因为没有结果就当作未开始，`unknown` 更不能自动重试。真实系统可以通过远端查询和去重键把状态收敛为 `committed` 或 `failed`，但收敛证据必须追加到 Session。Memory 教学实现可以先用带时间与来源的静态条目，重点验证冲突和过期拒绝，而不是伪装成完整检索系统。

## 常见误区

第一，把聊天页面仍能打开写成「完整 Session 可恢复」。UI 文本可能缺少工具结果、审批和提交状态；恢复对话不代表能安全恢复副作用。

第二，把 Context 当数据库。Context 会被裁剪、重排、协议适配并受窗口限制，不能承担唯一审计来源。

第三，把 Compaction 叫作无损记忆。摘要会遗漏或重述，截断更会直接丢弃模型可见内容。自检摘要不是数学证明。

第四，把 Cache 当 Memory。Cache 复用相同或兼容的计算前缀，Memory 检索相关材料；压缩改变前缀后，Session 延续也不保证 Cache 命中。

第五，从目录或类型名推断外部 Memory 默认存在。只有看到配置、调用链、存储、检索和测试，才能登记能力状态；否则保持未知。

第六，恢复时逐条重放工具事件。事件回放用于状态归约，命令重放会再次产生副作用。两者必须由不同接口和权限边界承载。

## 验证方法

先验证 Session 身份与持久性。创建两个会话和一个子会话，追加有序事件，关闭并重启进程，再检查列表、父子关系、顺序、删除和并发写入。内存参考实现只能用于契约测试，不能作为跨进程持久性证据。

再验证 Context 构造。固定一组 Session 事件，改变分支、模式、工具集合和运行时指令，保存每次实际送给 Provider 的规范化请求。断言已完成工具调用与结果仍正确关联，隐藏条目不泄漏，且 Context 的变化可追溯到明确转换。

然后验证 Compaction。构造包含精确路径、否定约束、失败工具结果和未决操作的长历史，触发自动与手动压缩，检查摘要、保留尾部、令牌变化和失败回退。再次构造 Context 时，应能指出每条关键信息来自原始事件、摘要还是运行时注入。

接着验证 Cache 与 Memory。比较压缩前后的请求前缀和缓存指标，不从 Session ID 推断命中；为 Memory 注入过期、冲突、越权和无关片段，断言检索结果带来源与时间，并能被权限和冲突规则拒绝。项目没有 Memory 时，测试应明确不适用，而不是伪造功能。

最后做崩溃恢复实验。在工具开始前、外部副作用后但结果落盘前、结果落盘后分别强制终止进程。恢复器必须区分未开始、状态未知和已提交；对已提交调用零次重放，对可重试调用复用去重键，并保存环境核验或人工判断。恢复不是重放。没有这组故障注入，最多只能证明「能继续聊天」。

## 验证练习

建立一个包含十二条事件的 Session：两次用户输入、两次模型响应、一次文件写入、一次远端发布请求及其未决状态。先生成未压缩 Context，再用一个刻意漏掉文件路径的摘要替换早期模型可见历史，最后加入一条过期 Memory，声称远端发布已经完成。

验收时比较三份数据。Session 归约结果必须仍能找到文件写入的提交证据；Context 应明确路径只存在于原始事件而摘要遗漏；过期 Memory 不能覆盖未决发布状态。随后分别在发布开始前、远端成功但结果未落盘、结果已提交三个位置模拟崩溃，断言重启后只有第一种可以直接执行，第二种先查询远端，第三种零次重放。

作品应包含事件 JSONL、两份 Context 快照、摘要来源范围、Memory 拒绝理由和三次恢复判定。复核者需要能从 Context 中每段文字反查来源，也能从未决调用反查外部核验。完成这些不代表摘要忠实度已得到统计保证；它证明的是权威记录、派生视图和副作用恢复没有被混成同一状态。

## 自检

### 问题 1

Session ID 没变，为什么下一次模型看到的内容仍可能变化？

**答案：** Context 是从 Session 路径、摘要、指令、工具和运行时信息派生的单次请求视图。新增事件、分支、压缩或模式切换都会改变它。

### 问题 2

压缩摘要说远端发布已完成，恢复器可以直接信任吗？

**答案：** 不可以。摘要是有损派生材料，应核对结构化调用记录、去重键和真实远端状态，再决定补记、重试或人工处置。

### 问题 3

外部 Memory 检索到一条高度相关记录，是否等于它应该进入 Context？

**答案：** 不等于。还要检查来源、时效、权限和与当前权威状态的冲突；Memory 是候选输入，不是 Session 真相。

### 问题 4

为什么「Session 不等于 Context」使用 D 级 Claim？

**答案：** Claude 公共 SDK、pi 和 Gemini CLI 的锁定实现分别证明存储、投影与压缩表面；把它们归纳为跨 Harness 的共同生命周期是分析推断，各项目的持久性、删除、恢复和 Memory 语义仍需单独核验。
