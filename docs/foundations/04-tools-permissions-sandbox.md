# 工具、权限与 Sandbox

## 读者会得到什么

本页把一次有副作用的工具调用拆成五道门：工具是否暴露、参数是否有效、策略如何决策、是否需要用户批准、平台隔离是否真正生效，最后才是执行环境中的副作用。读完后，你应该不会再把「有一个工具」「弹出了确认框」「运行在容器里」分别误写成完整安全保证。

你还会学会怎样描述能力状态。同一项目的 Sandbox 可能在 Linux 默认可用、在 Windows 依赖另一后端、在远程执行模式交给外部服务，或在某些客户端没有证据。文章必须写出默认、可选、扩展、外部、缺失、未知或不适用，以及对应平台和模式；颜色、营销名称和目录名都不能替代这些限定。

授权不是隔离。隔离也不是授权。

## 核心概念

### 五道门分别回答什么

第一道门是工具暴露。注册表决定当前模型能否看到工具名称、说明与参数 Schema；模式、项目配置、扩展和客户端能力都可能改变集合。工具没有暴露时，模型通常不能按正规协议调用它；工具已经暴露，也只表示模型可以提出候选行动，不表示调用会获准。

第二道门包含参数校验与策略。语法层确认 JSON 和 Schema，语义层检查路径、命令、资源与项目约束，策略层再根据工具、参数、工作区信任、模式和持久规则给出允许、拒绝或询问。三者经常由不同模块完成。把它们压成一个布尔值，会丢失错误来源，也很难证明默认行为。

第三道门是用户批准。只有策略要求询问时，交互表面才需要把调用、风险、范围和可持久化选项呈现给用户。批准应绑定具体对象和范围，不能把一次文件写入批准扩成永久网络访问。非交互模式如何处理询问也要明示：拒绝、失败、使用预授权，还是交给外部控制面。

第四道门是 Sandbox 或其他隔离后端。它把抽象权限物化为文件、进程、系统调用、网络和资源约束。容器、Bubblewrap、Seatbelt、受限令牌、文件系统 ACL 或远程执行服务的覆盖范围不同；后端名称相同，也可能因平台版本和配置产生不同强度。

第五道门才是真实执行。这里产生进程、文件与网络副作用，返回输出、退出状态和拒绝证据。执行成功不代表任务正确；执行失败也不自动说明 Sandbox 工作，可能只是命令本身出错。需要把策略决定、隔离准备和系统结果分别记录。

门要逐一通过。证据也要逐一留下。

### 为什么批准不能证明隔离

用户批准回答的是授权问题：在看见的描述和范围下，是否同意 Harness 尝试这个动作。它不检查操作系统最终采用哪种隔离，也不保证参数在批准后没有被替换。若审批 UI 与执行记录缺少同一调用标识和参数摘要，甚至无法证明被执行的是用户看见的那一个动作。

隔离回答的是能力问题：即使进程恶意或 Harness 判断失误，它实际能读写哪些路径、能否联网、能否派生进程。Sandbox 可以阻断已经批准的越界行为；它也可以允许策略本来就不应授权的工作区内破坏操作。因此两层需要纵深防御，不能互相替代。

策略允许同样不是 Sandbox。`ALLOW` 可能只表示无需再问用户，后续仍应在受限后端执行；也可能在某个明确模式下允许无沙箱执行。正文必须沿调用链核对实际执行请求，而不是从决策枚举名称推断隔离状态。

### 锁定实现中的分离证据

Gemini CLI 的 `packages/core/src/policy/policy-engine.ts:290-298` 单独配置默认策略：交互模式默认询问，非交互模式默认拒绝；`562-571` 的 `check()` 接收工具调用并返回策略结果。上游 `policy-engine.test.ts:144-153` 验证默认询问和自定义拒绝。这些证据说明策略引擎拥有授权决策表面。

隔离则有另一条源码链。`packages/core/src/sandbox/linux/LinuxSandboxManager.ts:140-149` 明确把 Linux 实现描述为基于 Bubblewrap 的 `SandboxManager`；`208` 之后的 `prepareCommand()` 构造隔离命令。上游测试 `LinuxSandboxManager.test.ts:75-92` 断言结果通过 `bwrap` 包装。策略测试通过，不能替代这条隔离测试。

Codex 的锁定源码给出更直接的边界。`codex-rs/core/src/tools/sandboxing.rs:386-400` 在 `SandboxAttempt` 中同时保存具体 `sandbox` 类型和 `sandbox_requested`，注释明确后者表示策略请求隔离，独立于主机的具体包装器。`sandboxing_tests.rs:292-305` 模拟 Windows 后端不能强制 deny-read 的情况，并断言拒绝无沙箱运行。

这些事实支持「授权与隔离可以分别观察」。跨项目结论仍保持 D 级，因为默认决策、审批缓存、后端、平台覆盖和降级策略并不相同。Gemini CLI 的 Bubblewrap 测试只覆盖锁定 Linux 实现；Codex 的 Windows 测试也不能证明其他模式同样失败关闭。

### Hook 和安全检查器位于哪里

Hook 可以在工具调用前后观察、修改、拒绝或请求额外判断，具体能力取决于它接入核心策略的位置。若 Hook 只是 UI 通知，它不是授权边界；若核心执行器强制等待 Hook 结果，它可以成为策略链的一部分。无论哪种情况，普通进程内 Hook 都不能自动变成 OS 隔离。

安全检查器同理。它可以分析命令、路径或模型风险，输出拒绝或询问；但它的可用性、超时、失败策略和绕过路径需要测试。检查器报错后默认允许是高风险事实，必须明确登记；默认拒绝也要区分产品不可用和安全阻断。

## 最小例子

考虑一个结构化写入调用，目标是工作区外的路径。下面仍是仓库级说明格式，不是任何产品的实际 API，也不会在本仓库执行：

```json
{
  "call_id": "W42",
  "tool": "write_file",
  "args": {
    "path": "../outside/secret.txt",
    "content": "replacement"
  }
}
```

第一道门可能通过，因为 `write_file` 已注册并对当前模式可见。第二道门的 JSON 与 Schema 也可能通过，因为 `path` 和 `content` 都是字符串；但路径语义检查应解析实际目标，发现它越出允许根目录。此时策略应拒绝，执行开始事件不应伪装成已经发生。

假设某个错误实现漏掉路径语义检查并向用户询问。用户批准只说明授权表面返回允许，不能让越界路径自动安全。第四道门仍应把文件系统权限物化到允许根目录，使操作系统或远程执行服务拒绝写入。这个拒绝是纵深防御，不是省略路径检查的理由。

如果隔离后端不可用，系统要有显式结果：失败关闭、请求改变模式、转交外部受控执行，或在明确高风险配置下无沙箱运行。任何选择都必须出现在 Trace 和 Claim 限定中。静默回退到宿主机执行会让「Sandbox 已启用」成为假结论。

反过来，即使目标路径在工作区内，批准也不自动合理。写入可能覆盖关键配置，策略仍可要求确认；Sandbox 通常允许工作区写入，不会替用户判断业务意图。授权和隔离解决不同威胁。

### 能力状态怎样写

`default` 表示锁定模式走标准路径就启用，必须有调用链或测试；`optional` 表示核心实现存在但需要配置；`extension` 表示由插件、Hook 或额外组件接入；`external` 表示保证主要来自容器、远程服务或宿主平台。四者都不是质量等级。

`absent` 只能在明确检查的范围内使用，例如某平台和模式的锁定源码确认没有该后端；`unknown` 表示证据不足，不能为了填矩阵写成缺失；`not-applicable` 表示该维度本身不成立。一个项目可以在 Linux 为默认、Windows 为可选、Web 客户端为外部、闭源服务内部为未知。

### 失败与回退

策略解析失败、审批通道断开、隔离准备失败和命令执行失败是四类不同事件。解析失败可以拒绝或询问；审批断开不能伪装成用户拒绝；隔离准备失败不能写成工具业务错误；命令退出非零也不能证明隔离拒绝。失败分类决定恢复、告警和 Eval 统计。

允许升级权限时，要记录谁请求、为何请求、增加哪些文件或网络权限、是否只对本次调用有效，以及升级后实际采用的隔离配置。缓存批准需要作用域和失效条件。仅记录「已允许」无法审计权限是否扩大。

## 常见误区

第一，把工具存在写成默认可执行。注册和暴露只到第一道门，后面还有参数、策略、批准、隔离和环境。

第二，把权限弹窗叫作 Sandbox。弹窗是授权交互，Sandbox 是执行隔离。两者可能由不同进程、不同平台组件完成。

第三，把容器等同绝对安全。容器的挂载、网络、特权、内核共享和逃逸面需要具体配置证据；容器外还可能有凭据代理或远程工具。

第四，把 Hook 当不可绕过边界。只有核心执行路径强制调用、处理超时并失败关闭时，Hook 才可能承担策略职责；它仍不自动提供操作系统隔离。

第五，用颜色表示安全状态。红绿图无法表达默认、可选、外部或未知，也不利于无障碍阅读。图与矩阵必须同时给文字状态、平台、模式和证据等级。

## 验证方法

先验证工具集合。对每种模式生成模型可见工具清单，确认未注册、被禁用和扩展工具的差异；工具描述和 Schema 也要快照化。模型幻觉出一个未知工具时，Harness 应产生可追踪拒绝，不得进入真实执行。

再验证策略与批准。为允许、拒绝、询问、非交互、工作区不可信、路径越界和持久批准分别构造测试，断言决策、理由和调用标识。审批展示的参数摘要要与执行前摘要一致，防止批准后替换。

然后验证隔离。使用临时 fixture 尝试读取允许路径、拒绝路径、写入工作区、写入工作区外和访问网络；断言后端实际命令、系统拒绝和副作用。测试应覆盖后端不可用与不支持的权限组合，确认不会静默无沙箱运行。

接着验证组合矩阵。策略允许且 Sandbox 拒绝时，应报告隔离拒绝；策略拒绝时，不应启动隔离执行；用户取消时，不应留下副作用；外部执行时，要保存远端权限和结果证据。每个分支都需要独立事件。

最后进行对抗检查：故意让 Hook 超时、策略解析器报错、审批通道断开、隔离包装器不存在、工作目录使用符号链接，并检查系统是否失败关闭。通过单元测试只证明构造逻辑；涉及 OS 边界的结论还需要对应平台的集成实验，缺少时不得升级为 A 级。

## 自检

### 问题 1

用户已经批准命令，为什么仍要使用 Sandbox？

**答案：** 批准只表达授权，不能保证参数无误或进程诚实。Sandbox 限制实际可访问资源，在策略或实现失误时提供独立防线。

### 问题 2

命令在容器里运行，是否可以省略策略检查？

**答案：** 不可以。容器只限制部分资源，不判断业务意图；工作区内的破坏操作可能完全被容器允许，仍需策略与用户授权。

### 问题 3

隔离后端不支持某项 deny-read 权限时，什么证据最关键？

**答案：** 要看到准备阶段明确失败，并确认没有回退到无沙箱执行。Codex 的锁定 Windows 测试就是此类项目证据，但不能自动外推到其他平台。

### 问题 4

为什么「权限决策不等于 Sandbox」是 D 级 Claim？

**答案：** Gemini CLI 与 Codex 的源码和测试分别直接证明项目内策略与隔离表面分开；把它们提升为跨 Harness 的共同安全边界是本仓库的分析推断，默认值和平台行为仍各不相同。
