# 决策与事故复盘方法

## ADR 模板

```markdown
# ADR-NNN：标题

- 状态：proposed / accepted / superseded / rejected
- 日期与决策者：
- 适用 source SHA / config：

## 背景与约束
## 目标 / 非目标
## 证据与不确定性
## 备选方案
## 决定与理由
## 安全、兼容、成本和许可证影响
## 验证门禁
## 回退方案
## 重新评估触发器
```

被拒方案仍然保留，因为后续约束可能改变。用 source/test/runtime/community/inference 标签区分证据。

## Postmortem 模板

```markdown
# PM-NNN：用户可观察的故障

- 状态 / 严重级别 / 时间范围：
- 影响版本、环境和用户：
- 首次发现与恢复时间：

## 摘要与影响（不夸大、不淡化）
## 事实时间线（UTC、证据链接）
## 直接原因
## 系统性根因与促成条件
## 为什么检测、测试和评审没有发现
## 修复、回滚与剩余风险
## 防复发门禁（负责人、期限、可验证退出标准）
## 哪些文档/假设需要修正
```

不写“某人粗心”；分析为什么系统允许一个合理局部动作绕过真实入口、语义断言或运行时事实。

## 根因证据要求

根因必须能解释现象、时间线和反事实：移除该原因，故障应消失；重新引入，定向测试应失败。日志相关不等于因果。多个独立 bug 产生相同错误时分别建因果链。

## 防复发措施优先级

1. 真实产品路径上的自动化门禁；
2. 结构化不变量与失败关闭；
3. 可观察运行时事实和错误归因；
4. 静态检查/生成器 guard；
5. 文档和培训。

只加文档通常不足以关闭代码或系统风险。每项措施记录 owner、deadline、验证测试和回归时的预期失败信号。

## Atlas 的决策索引

每次主 source lock 提升、许可证边界变化、协议基线变化、benchmark scorer 变化、安全例外或目录/生成策略变化，都应产生 ADR。外部项目的 postmortem 只做链接与摘要，Atlas 自身事故才使用本仓库 PM 编号。
