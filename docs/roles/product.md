# 产品负责人：从用户任务到可解释体验

## 适用角色

本路径面向设计 Agent 产品、开发者体验、任务工作流、权限交互和多端体验的产品负责人。你要把「帮用户完成工作」拆成可观察的阶段，让用户知道系统在做什么、需要什么授权、哪里失败以及怎样恢复。

选型时不要从功能清单出发。先固定用户场景、工作物和风险等级，再比较六类 Harness 如何形成模型输入、调用工具、保存会话、扩展能力和暴露客户端。正式比较入口从 [运行时、配置与模型输入](../comparisons/01-runtime-config-model-input.md) 开始。

## 学习目标

完成后，你应能为低风险只读、可回滚写入和高风险外部操作分别定义成功产物、允许动作、确认范围与失败语言；能把模型响应、工具状态、Harness 终态和独立验收映射成不会过度承诺的产品状态；还能解释 Session、子任务和多客户端之间哪些事实共享、哪些只属于本地界面。

你还应能用证据管理产品路线。源码入口、公开契约、确定性实验、真实用户研究和生产指标支持的结论不同；能力尚未验证时必须显示为计划、受限或未知。最终结果是一套可测试任务体验与发布判据，而不是功能数量或一次精彩演示。

## 前置知识

不要求编写 Harness 核心，但需要能阅读结构化事件、任务验收和基本统计报告，理解工具调用会产生文件、进程、网络和凭据风险。建议先完成职责边界、真实 Turn、权限与 Sandbox 三篇共同基础，再阅读循环工具与权限恢复两篇比较。

准备三个合成用户场景和一个可点击或文本化原型即可。所有外部操作使用本地假服务；每个场景预先写明正确产物、不可接受副作用、时间预算与人工接管条件。用户研究记录要区分理解度、偏好和任务是否正确，避免把满意度当作唯一质量证据。

## 决策问题

产品首先要定义成功对象。是回答文本、修改后的工作树、外部工单、可审计报告，还是多项产物组成的 Goal？若验收对象不清楚，界面很容易把「模型停止输出」显示成「任务已完成」。

其次决定人机边界。哪些操作可自动执行，哪些必须确认，确认应展示命令、目标、影响范围还是凭据作用域？批准、拒绝、修改参数和永久规则需要不同结果，不能只有一个模糊的继续按钮。

还要定义失败语言。配置缺失、模型不可用、权限拒绝、工具错误、网络中断、上下文溢出和产品验收失败应分别呈现。用户需要知道哪些错误可以重试，哪些需要修改任务，哪些已经产生外部副作用。

成本与速度也要绑定任务价值。首字延迟、总时长、工具等待、人工确认和模型用量应分开记录；缓存或更快模型降低成本时，仍需验证上下文、工具结果与正确率没有退化。高风险任务宁可慢一些，也不能隐藏验证和授权步骤。

上线范围应由能力证据决定。某个 Harness 在本地演示中完成任务，只能说明该配置和样本可运行；企业身份、共享项目、并发、长会话、移动网络与客户数据仍需单独验收。产品路线图要把未知项列成验证任务，不能把计划中的能力显示成已可用。

## 工作流

1. 选取三个真实任务：低风险只读任务、可回滚写入任务、高风险外部副作用任务。为每个任务写输入、产物、时间预算、允许动作、禁止动作和人工验收条件。
2. 按 [模型—工具—权限—执行循环](../comparisons/02-loop-tools-execution.md) 设计界面状态，明确等待模型、等待确认、正在执行、正在恢复、部分完成、失败与取消。每个状态只承诺已获得的事实。
3. 为 Session、子任务和多个客户端设计可见关系。展示父子任务、当前目录、模型、权限和重要产物；将窗口、草稿与格式留在客户端，不让局部状态污染共享任务结论。
4. 用版本化任务做可用性和正确性评测。体验指标观察时延、确认负担和恢复率，独立 Scorer 检查产物；两类指标共同参与决策，不能用满意度替代任务正确。

## 实践任务

设计一个「检查并修改项目配置」的三风险原型。只读场景展示来源和差异；写入场景先给出目标、范围和可逆性，再请求一次性批准；高风险场景模拟向外部系统发布，必须展示身份、幂等键、不可逆范围和二次确认。每个界面状态只引用已经发生的事件，模型说完成时仍保持「待验收」。

为原型准备八个失败剧本：配置缺失、模型不可用、权限拒绝、用户取消、工具错误、执行后回执丢失、Context 压缩遗漏和独立 Scorer 失败。用户需要看见失败属于哪一层、已有副作用、可选恢复和是否需要人工接管。重试按钮必须明确会继续同一 Session、创建恢复 Attempt 还是重新开始任务。

邀请另一位评审者用固定脚本完成三场景，记录状态理解、错误归因、确认负担、耗时和最终 Artifact。根据结果修改文案和状态机，再用相同脚本复测；不能因为用户喜欢动画就删除关键边界，也不能因为一条任务通过就宣布整个场景上线。

原型还要展示证据层级。每个关键状态提供「查看依据」入口：配置选择回到有效设置摘要，权限决定回到动作和作用域，执行结果回到文件或外部服务，验收回到 Scorer。思考摘要和进度文案可以隐藏细节，但不能成为唯一依据；敏感参数在展示前脱敏，同时保留受控审计引用。

为多端场景加入断线与竞态。桌面端批准后，编辑器端应看到服务端决定，但两个客户端的草稿和选中项互不覆盖；旧客户端重连时不能用过期参数再次执行。父任务取消后，界面分别展示子任务、后台进程和外部事务的确认状态，避免一个「已取消」横幅掩盖仍在运行的工作。

最后做一次发布前反向评审：假设指标上涨来自更宽松的成功定义、更多重试或隐藏严重失败，逐项寻找反证。若缺少证据，产品状态保持受限或实验，不用路线图日期填补。只有锁定场景、正确性、严重风险和恢复体验都达到预设门槛，才进入更大范围验证。

## 风险与边界

过度自动化会隐藏风险，过度确认则让用户机械点击。确认策略应由操作影响、可逆性、数据敏感度和环境信任共同决定，并允许组织策略收紧。用户一次批准不能默认为未来所有目录和会话授权。

计划、思考摘要和进度动画都是产品投影。它们有助于理解，却不是系统执行事实；关键结论仍要回到工具事件、文件散列和外部系统状态。子任务摘要也不能掩盖子任务失败或未授权副作用。

反馈按钮只代表特定时刻的用户信号。它可能受结果可见性、任务难度和自选择偏差影响，不能直接作为质量总分或训练奖励。反馈用途、保留和退出机制要清楚告知用户。

## 验收清单

- 每个核心场景都有明确成功产物与失败分类。
- 权限提示展示动作、目标、作用域、风险和可逆性。
- UI 能区分配置、连接、模型可见、批准、执行与验收状态。
- 取消和重试说明是否可能留下文件、进程或外部副作用。
- 父子任务和多端共享范围清楚，客户端局部状态不会冒充服务端事实。
- 用户反馈、体验指标、任务评分与发布门禁分别定义。

## 作品证据

作品集包含三份任务契约、产品状态机、权限提示原型、八个失败剧本、用户研究记录、最终 Artifact 与独立评分报告。状态机要把等待模型、等待批准、执行、核验、恢复、部分完成、失败和取消分开，并标出每个状态的数据来源。

再提交一页发布决策：哪些场景达到门槛，哪些仅适合受限试用，哪些因证据不足保持未知；同时列出正确性、严重副作用、时延、确认负担和成本。该作品证明你能把 Harness 证据转成可解释体验，不证明真实客户部署已经获得授权或生产规模下同样可靠。

建议补充一份状态文案词典，逐项规定「已连接」「已批准」「已执行」「已核验」「已发布」的证据来源和禁止含义。设计、工程和支持团队使用同一词典后，界面、日志与事故沟通不再用同一个「成功」覆盖不同阶段，也便于后续自动化验收。

## 自检

### 问题 1

模型说「已完成」时，界面能否直接显示成功？

**答案：** 不能。产品必须等待产物或外部状态通过验收，模型文本只能作为候选说明。

### 问题 2

所有工具调用都弹窗是否最安全？

**答案：** 未必。机械确认会削弱判断，应按影响与可逆性分级，并由系统隔离承担真正边界。

### 问题 3

重试按钮要说明什么？

**答案：** 说明失败类型、是否会新建 Attempt、已有副作用和可能重复执行的风险。

### 问题 4

产品指标为什么不能只有完成率？

**答案：** 完成率可能受重试和宽松判定影响，还要结合正确性、风险、恢复、时延、成本与失败簇。
