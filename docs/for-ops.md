# 成本、部署与风险：给做决策的人

*这一篇讲给要为这类工具做技术选型、算账、担安全责任的人。读完你能回答：账单由什么决定、部署形态有哪些、风险边界在哪、以及上线前该验证什么。不需要读代码。*

两个部门会先后找上你。财务问：为什么这个月的模型账单是上个月的三倍，用的人并没有变多。安全问：这东西能不能删了我们的代码，你给个准话。

两个问题都答不了「看情况」。第一个的答案是一个可以监控、可以告警的数字，第二个的答案要分成三层说，而且其中一层跟沙箱、审批都没关系。

如果你还不清楚 harness 是什么，先看 [不写代码也要懂的：agent harness 到底是什么](concepts.md)。

## 一、账单由什么决定

### 计费的三种 token

调用模型时，一次请求的账单拆成三部分：

| 类别 | 说明 | 价格 |
|---|---|---|
| **未命中的输入** | 这次新发的、缓存里没有的内容 | 标准输入价 |
| **命中缓存的输入** | 开头那段和上次相同，直接复用 | 按 provider 的缓存价，DeepSeek 公开定价是标准价的 **1 折** 左右 |
| **输出** | 模型生成的内容 | 最贵 |

折扣率来自 provider 的公开定价，不是本仓库实测出来的；换 provider 要重新查。

DeepSeek 的接口会直接告诉你这次命中了多少（`prompt_cache_hit_tokens`）、没命中多少（`prompt_cache_miss_tokens`），两者相加等于总输入量。别家还有第四类「缓存写入」要单独计费，DeepSeek 不上报这个指标，所以在它上面只有三类。

一个容易算错的地方：**推理 token（reasoning）已经包含在输出里了**，做成本汇总时不能再加一遍，否则会高估。

### 命中率是账单的主要杠杆

我们用真实 API 实测的数据（完整记录在 `research/runtime-evidence/2026-08-16-deepseek-cache-probe.md`）：

| 场景 | 命中率 |
|---|---|
| 前缀稳定、只在末尾追加 | 81%–96% |
| 只改了请求开头一句话 | **0%** |
| 会变的状态写进请求开头，每次切换 | 33% |
| 同样的状态改为追加在末尾 | 81% |
| 压缩时复用主对话开头 | 93.4% |
| 压缩时另写一段开头 | **0%** |

把命中率从 30% 提到 85%，输入成本大致降到原来的三分之一左右（因为命中部分按一折算）。**这不需要换模型，也不改变任何用户可见的功能。**

### 怎么监控

dsh 把每次请求的用量记进会话日志，界面上按 `命中 ÷ (未命中 + 命中 + 写入)` 显示命中率。

**运维上值得建的一条告警**：命中率突然跌到接近 0。这通常意味着请求开头被改动了。dsh 的日志里有个直接的线索——出现 `request/header` 且原因标记为 `change` 的事件，说明请求头变过。往前找到那一步，就知道是什么动作导致的。

这条线索会误报：采样参数（`temperature`、`maxTokens`、`stop`）变化也会写同一条事件，而它们根本不占 prompt token，不影响前缀匹配。所以要拿它跟命中率一起看，不能单看事件本身。dsh 自己对前缀稳定性没有任何运行时断言，也不自带告警，命中率塌了只能事后从用量里看出来。

Claude Code 团队的公开做法更直接：**把缓存断裂当作线上事故来告警**。

### 会让缓存失效的操作清单

拿去做 checklist：

- 改 system prompt 的任何一个字（从第一个 token 起全废）；persona 换了也算
- 工具的定义或**顺序**变化
- 切换模型或 provider（等于换一个缓存域）
- 触发压缩，或者单独剪掉某条工具结果（都从被改写的那条消息起往后重算）
- 进出「计划模式」这类会改提示词的模式（dsh 会作废被改动的那一段往后的内容；Claude Code 把它做成工具因而不受影响）
- 插件热插拔、MCP 服务连断
- 开 continuable 子代理或 fork（请求头多出增量，继承来的那段历史全废，而且这条没有响亮的失败信号）
- 任何一个插件写了会随时间变化的 system 段落（比如往里塞时间戳），会导致每一步全部未命中
- 换个部署实例（如果新实例的启动配置不同）

「改推理强度」这类调用参数会让 dsh 写一条请求头变更事件，但它们不占 prompt token；它们到底会不会改变 provider 侧的模板前缀，上游仓库里没有说明，本仓库也没测过。

## 二、部署形态

dsh 的命令行是「两个自动初始化的 profile + 一个 plugin 子命令」：

| 入口 | 形态 | 适合 |
|---|---|---|
| `dsh web`（即 `dsh --profile web`） | 起一个本地 HTTP 服务，浏览器交互 | 个人日常使用 |
| `dsh --profile headless "任务描述"` | 一次性驱动器，跑完打印答案就退出 | CI、批处理、自动化 |
| `dsh plugin --profile <名字> <pnpm 参数>` | 管理某个 profile 的插件，参数转发给 pnpm | 二次开发 |

`--profile` 后面的名字没有白名单，任何 profile 名都能填，web 和 headless 只是发行版自带模板的两个名字。

程序化接入有三条路：

- **SDK**（JSON-RPC over stdio）：自己的程序驱动它；
- **ACP**：dsh 作为**被驱动方**，接入编辑器或上级 agent；
- **MCP**：dsh 作为**消费方**，把外部工具接进来给模型用。

方向别搞反：ACP 是「别人驱动 dsh」，MCP 是「dsh 用别人的工具」。

另外它还能把 **Claude Code、Codex、任意 ACP agent、另一个 dsh 当子代理来驱动**，这一项别家都没有。

它也桥接这两家的 hook 协议，但覆盖面要打折：Claude Code 那边 30 多个事件只接了 7 个、5 种 handler 只跑 `command` 一种，Codex 那边不支持 `ask` 决策。已有的 hook 能不能直接搬过来，得逐条对。

**注意**：终端 UI（TUI）已经在 2026-08-04 被上游删除了，现在的交互面只有 Web。做终端场景的规划时要知道这一点。

## 三、风险边界

### 沙箱能挡什么、不能挡什么

沙箱是操作系统级的隔离，dsh 在三个平台上一共有四个后端（Linux 的 bubblewrap 和 Landlock 两个、macOS 的 Seatbelt、Windows 的受限令牌 + ACL）。三档模式：只读、可写工作区、完全放开。

两条限定要一起记住，否则会高估它：

- **Windows 那个后端只声明「部分兑现」**。受限令牌要能完成进程初始化就得让 Everyone 出现在限制列表里，于是外部对象只要给 Everyone 授过写权限，在沙箱里仍然可写；NTFS 硬链接还能把工作区内的文件别名到工作区外。上游把这个缺口写进了后端的返回值，没有藏在一句「已启用沙箱」里。
- **沙箱只管文件效果，不管网络、不管进程可见性、不管凭据**。`bash` 里 `curl` 一个内网地址，沙箱不会拦。另外 `write` / `edit` 走的是进程内的路径围栏，不是内核沙箱。

**它挡的是文件操作越界。** 它不能挡住的是：网络出口，以及插件本身。

这一点上游写得很直白：一个插件运行在宿主进程里，天然拥有宿主进程的全部权限。所以**装第三方插件等于装一个有完全权限的程序**，跟「让模型跑一条命令」是完全不同量级的信任决策。

### 审批的失效模式

审批是弹窗问人。它的失效模式不是技术问题，是人的问题——**用户点习惯了「同意」**。

各家的应对：Claude Code 有一种模式是用第二个模型当自动审核员；Codex 的 guardian 机制类似，而且做成了 fail-closed（超时或判断不了一律拒绝）。dsh 默认干脆不弹窗，靠沙箱兜底，只在模型主动申请提权时才问人；hook 桥也能返回「要问」，但默认组合里没挂任何 hook 桥。

Claude Code 闭源，这一列全部依据官方公开文档，无法从源码核实，做安全结论时要给它留出这份不确定。

**选型判断**：一个只有审批、没有系统级沙箱的产品（OpenCode 就是），安全边界实际上是纸面的。Claude Code 在**原生 Windows 上没有沙箱**，这一点在 Windows 团队里值得单独评估。

### 凭据

dsh 的原则是**配置里只放引用，不放密钥**：组合配置写的是 `apiKeyEnv: DEEPSEEK_API_KEY` 这样一个名字，值由凭据服务去解析，没有凭据服务时才回落到启动环境变量。

要注意 key 仍然可能落在磁盘上：启动时会读调用目录下的 `.env` 和 harness home 里的 `.env`（优先级是继承环境 > 调用目录 `.env` > harness home `.env`）。所以「不进配置文件」不等于「不落盘」，部署到共享环境或 CI 时这两个 `.env` 要单独管。

### 数据边界

模型请求里会包含什么，取决于 harness 拼了什么：项目说明文件的内容、被读取过的文件片段、工具执行的输出、当前工作目录路径。做合规评估时，这几项都要算进「会离开本机的数据」。

## 四、选型对照

六个 harness 在关键决策项上的差别：

| | dsh | Claude Code | Codex | OpenCode | pi | mini-swe-agent |
|---|---|---|---|---|---|---|
| 开源 | 是 | **否** | 是 | 是 | 是 | 是 |
| 系统级沙箱 | 有（Windows 只兑现一部分） | 有（**原生 Windows 无**） | 有（三平台） | **无** | **无** | 换环境实现 |
| 默认弹窗 | 否 | 是 | 是（策略受限时才问） | 是 | 无此机制 | 是（默认要确认，可改成不问） |
| 会话恢复 | 有 | 有 | 有 | 有 | 有 | **无** |
| 会话分叉 | 有 | 有 | 有 | **无**（只能撤销到某条消息） | 原生支持 | 无 |
| 压缩 | 有 | 有 | 有（三套兜底） | 有 | 有 | **无** |
| 能替换主循环 | **能** | 否 | 否 | 否 | 否 | 不适用 |
| 把别家 agent 当子代理驱动 | **能**（Claude Code / Codex / 任意 ACP agent / 另一个 dsh） | 否 | 否 | 否 | 否 | 否 |

完整的七维机制对照见 [14 横向对照](14-comparison.md)。

**一句话取向**：要「一个能用的编程 agent」，选 Claude Code 或 OpenCode；要「一个能长出很多种 agent 的底座」，dsh 的插件化是它最独特的地方，代价是理解成本最高。

## 五、上线前该验证什么

这几项都能在不接生产数据的情况下验证：

1. **命中率基线**：跑一个多轮任务，逐步记录命中率。第一步接近 0 是正常的，之后应该稳定上升。中途突然掉到 0，去找那一步之前发生了什么。
2. **压缩行为**：把上下文喂到接近上限，观察压缩何时触发、压完模型还记得什么。这决定了长任务的可用性。
3. **沙箱确实生效**：让它尝试写工作区外的文件，确认被拒绝，并且拒绝信息能让模型理解（而不是当成命令写错了反复重试）。
4. **凭据不落盘**：跑完检查配置文件、日志、临时目录里有没有 key。
5. **恢复**：中途杀掉进程，确认能接着跑，且模型看到的历史是完整的。

本仓库自己跑过的验证（上游两组端到端测试 + 我们写的缓存探针）记录在 [`research/runtime-evidence/`](../research/runtime-evidence/)，脚本在 `scripts/experiments/cache-probe.mjs`，可以直接拿去改。

## 自检

**Q1：老板说「换个便宜的模型省钱」，除此之外还有什么杠杆？**

缓存命中率。把命中率从 30% 提到 85%，输入成本大致降到三分之一，因为命中部分按一折计费。做法是保证请求开头稳定：会变的状态（权限、模式、时间）追加到末尾而不是拼进开头，工具顺序固定，避免会话中途切模型。这条杠杆不牺牲任何功能，用户完全感觉不到。

**Q2：安全评审问「这东西会不会删了我们的代码」，怎么回答才准确？**

分三层说。**沙箱**是操作系统级的，能把文件操作限制在工作区内，dsh 三个平台都有后端，这是真起作用的一层；但要说清它的边界：Windows 上只兑现一部分，`write` / `edit` 靠的是进程内路径围栏而不是内核，而且沙箱完全不管网络。**审批**是弹窗问人，它的失效模式是用户点习惯「同意」。**第三方插件**两层都挡不住：插件跑在宿主进程里，拥有进程的全部权限，装插件是一个独立的信任决策。另外要确认目标平台——Claude Code 在原生 Windows 上没有沙箱。

**Q3：为什么「上线前验证」里没有「跑一遍全部功能」这条？**

因为功能能跑通不代表边界正确。这套东西真正的风险集中在四个地方：成本随对话长度失控、压缩后模型丢失关键信息、沙箱看起来生效实际没生效、凭据意外落盘。这四项都要单独构造场景验证，跑一遍常规功能一个都覆盖不到。
