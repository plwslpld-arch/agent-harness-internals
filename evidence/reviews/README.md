# 阶段对抗复核记录

每个实施阶段结束后，都必须从“如何证明它没有完成”出发重新检查承诺、证据和边界。这里保存机器可读的复核记录；聊天中的口头说明、计划勾选或单次测试输出不能替代记录。

## 记录结构

每份 JSON 兼容 YAML 文件对应一个阶段，至少包含：

- `stage`、`date` 和被复核的完整 `commit`。
- `promises`：阶段承诺，每项具有稳定 `p-` ID 和中文陈述。
- `evidence`：文件、源码、测试、命令、渲染或人工复核证据；每项通过 `promise` 映射一个承诺。
- `findings`：反向检查发现的问题，标记 `high`、`medium` 或 `low`，以及 `open` 或 `resolved`。
- `resolutions`：使用与 Finding 相同的 ID，说明处理动作并引用证据。
- `commands`：实际执行的命令、真实退出码和结果摘要。不要只写“测试通过”。
- `result`：`pass` 或 `fail`。

`result: pass` 不能与未解决的高优先级问题并存，记录的最终命令退出码也必须全部为 0。测试先红后绿的失败过程保留在提交历史，阶段复核只记录最终验收命令。所有标记为 `resolved` 的 Finding 都必须有同 ID Resolution，且 Resolution 引用的 Evidence 必须真实存在。每个 Promise 至少要有一项 Evidence，避免用一条泛化测试替整阶段背书。

## 复核问题

每个阶段至少反问：是否遗漏用户明确要求；是否把草稿当完成；是否把结构通过当事实正确；是否把源码存在当默认能力；是否存在平台、模式、版本或闭源边界外推；是否有链接、图片、来源或命令只在本机成立；是否有高优先级问题被措辞掩盖。

执行 `npm run check:reviews` 校验已有记录。零份记录在施工期合法；阶段完成验收必须创建对应记录，最终部署前不得缺阶段记录。门禁证明记录内部一致，不证明人工判断本身没有遗漏。
