# 图示规范

图示用于降低理解复杂机制的认知负担，不用于装饰或填满页面。正式品牌 SVG 放在 `assets/brand/`，机制图放在 `assets/diagrams/`；两者都必须登记到 [`manifest.yml`](manifest.yml)。

## 何时使用哪种图

| 图示类型 | 适用问题 | 不适用情况 |
| --- | --- | --- |
| 架构图 `architecture` | 三个以上组件的边界、所有权、依赖或静态连接 | 只有一个步骤或一个事实 |
| 流程图 `flow` | 请求从输入到结果的处理步骤、分支和失败出口 | 强调参与者之间的先后消息 |
| 时序图 `sequence` | 用户、Harness、模型、工具和沙箱随时间交换消息 | 只想展示静态组件 |
| 状态图 `state` | Session、审批、任务或恢复机制的生命周期与转移条件 | 没有明确状态变化 |
| 数据流图 `data-flow` | Prompt、Context、Tool Result、Trace 或评测数据如何变换 | 只关心控制步骤 |
| 决策树 `decision-tree` | 权限、路由、失败恢复或发布门禁的互斥判断 | 分支并不影响结果 |

同一关系能用两句话说清时不必画图。每条主 Harness 至少需要一张中文系统架构图和一张端到端任务流程图；复杂文章再按实际需要补充时序、状态、数据流或决策树，不能为了数量重复表达同一件事。

## 中文与可访问性

每个 SVG 必须包含中文 `<title>` 和 `<desc>`。所有说明句、箭头标签和图例使用中文；Codex、MCP、Session、JSONL、函数名和协议字段等产品名或代码标识符可以保留。Manifest 的 `alt` 必须用中文说明读者从图中能获得什么，不得只写「架构图」或文件名。

每条 Manifest 记录包含 `id`、`path`、`type`、`scope` 和 `alt`。`scope` 指向使用这张图的读者页面；同一图可以服务一组紧密相关的章节，但不能成为脱离正文解释的结论清单。

## 渲染复核

提交前必须把 SVG 实际渲染为位图检查，而不是只看 XML：

1. 检查桌面宽度和窄屏宽度下是否裁切、溢出或字号过小。
2. 检查浅色与深色背景上的对比度，以及中文字体回退后的换行。
3. 检查箭头方向、分支标签、图例与正文描述是否一致。
4. 检查 `<title>`、`<desc>`、正文 `alt` 和 Manifest 是否表达同一范围。
5. 在 GitHub README 预览中复核一次；社交预览另导出规定尺寸的 PNG 并检查安全区。

视觉检查只能检查登记、中文元数据、明显英文句子和危险结构，不能证明图中的系统关系正确。关系正确性仍要回到锁定源码、正文解释和上游测试核对。
